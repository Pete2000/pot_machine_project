# 打锅机控制与转锅规则

## 1. 当前确认的机械规则

根据目前沟通，机器控制规则先按下面理解：

1. 设备有 4 个锅底出水口
2. 出水口编号与锅位关系如下
   `1 = 左上`
   `2 = 右上`
   `3 = 左下`
   `4 = 右下`
3. 单锅模式
   四个出水口同时出同一种锅底
4. 拼锅模式
   左侧 `1 + 3` 出一种锅底
   右侧 `2 + 4` 出一种锅底
5. 四宫格模式
   `1 / 2 / 3 / 4` 四个出水口分别出各自锅底
6. 设备还支持两个辅料出料口
   `鸡油`
   `骨膏`
7. 鸡油和骨膏出料口在左上角工位
8. 如果某个锅位需要鸡油或骨膏，而该锅位当前不在左上角，就需要人工转锅
9. 系统负责弹窗提示，人工转锅后点确认，再继续未完成步骤
10. 只要当前订单里存在需要鸡油或骨膏、但又不在左上角的锅位，就应优先先把其中一个转到左上角，再开始这轮执行
11. 如果有两个及以上锅位需要鸡油或骨膏，先完成当前左上角这一个，再提示人工转锅继续剩余锅位
12. 多个待选辅料锅位的当前固定优先级为
   `左上 -> 左下 -> 右上 -> 右下`
13. 人工转锅确认当前只使用安卓弹窗，不结合物理按键

## 2. 终端应该如何理解订单

终端最终不应该直接把接口样例当成 PLC 指令。

中间至少要拆成两层：

1. 订单解析层
   把后端订单解析成“锅型 + 锅位 + 锅底 + 口味 + 辅料”
2. 控制规划层
   把解析结果转换成“出水步骤 + 人工转锅提示步骤 + 辅料步骤”

也就是：

`接口订单 -> ParsedPotOrder -> DispatchPlan -> PLC 写寄存器`

## 3. 当前建议的内部控制模型

代码里已经预留了这一层模型，核心对象是：

1. `PotMode`
   `Single / Split / FourGrid`
2. `PotSlot`
   `TopLeft / TopRight / BottomLeft / BottomRight`
3. `PotFlavor`
   表示某个锅位实际要出的锅底和辅料
4. `ParsedPotOrder`
   表示“订单解析完成后的锅位任务”
5. `DispatchPlan`
   表示“可直接执行的控制计划”

## 4. 当前规划规则

### 单锅

1. 逻辑上只保留 1 份锅底定义
2. 执行时 4 个出水口一起出同一种锅底
3. 如果还要鸡油或骨膏，后面再追加辅料步骤

### 拼锅

1. 左侧锅底挂在左上逻辑槽位
2. 右侧锅底挂在右上逻辑槽位
3. 执行时
   左侧用 `1 + 3`
   右侧用 `2 + 4`
4. 如果右侧这一锅还要鸡油或骨膏，则先完成左侧和当前可做步骤
5. 然后弹窗提示人工转锅
6. 操作员确认后，再继续右侧未完成的水和辅料

### 四宫格

1. 四个锅位分别有各自锅底
2. 基础锅底按锅位逐个执行
3. 辅料按优先级执行
   `左上 -> 左下 -> 右上 -> 右下`
4. 只要存在需要辅料但当前不在左上的锅位，就应优先先把其中一个转到左上，再开始当前相位
5. 非左上锅位如果要鸡油或骨膏，该锅位的水和辅料应延后到它被转到左上后的相位
6. 当前左上锅位如果同时需要鸡油和骨膏，则两者允许同时执行
7. 系统先完成当前左上角可执行锅位
8. 然后弹窗提示人工转锅
9. 人工确认后，再继续剩余锅位未完成的水和辅料

## 5. `parentId` 的订单树关系

你刚确认了一个很关键的事实：

1. `parentId` 是把锅底订单串起来的关键字段
2. 每一条“锅型”记录是根节点
3. 每一条“锅底”记录挂在锅型节点下面
4. 每一条“口味”记录挂在具体锅底节点下面
5. 备注可能出现在锅底或口味节点上

当前可按下面方式理解：

1. `potTypeCode != null && parentId == null`
   表示锅型根节点
2. `potBottomCode != null && parentId = 锅型节点.id`
   表示锅底节点
3. `tasteCode != null && parentId = 锅底节点.id`
   表示口味节点

终端解析时，应该先按这棵树还原出每一个锅位真正的“锅底 + 口味 + 备注”。

## 6. 目前还缺的关键信息

这部分很关键，后面你补订单解析时我们就一起落掉：

1. 哪些口味编码或名称代表 `鸡油`
2. 哪些口味编码或名称代表 `骨膏`
3. 备注字段 `description` 到底是展示备注，还是也会参与配方控制
4. 拼锅场景下 `potSort` 的正式定义
5. 当有两个以上锅位需要辅料时，初始优先放左上的选择规则是否固定
6. 点击“加水”后，界面上哪些步骤算一个批次完成
7. 人工转锅确认后，是否需要重新校验当前订单仍然有效
8. 是否存在撤单、改单、转台时中断当前执行的规则

## 7. 对订单接口的额外要求

为了支持这套控制逻辑，后端或解析层最终必须明确输出这些字段：

1. 锅型
   单锅 / 拼锅 / 四宫格
2. 锅位号
   对于四宫格和拼锅，必须明确槽位
3. 锅底编码
4. 口味编码
5. 是否加鸡油
6. 是否加骨膏
7. 每种料的目标量
8. 是否需要人工转锅确认
9. 这条任务当前是否已撤销、已转台、已修改

## 9. 锅底配方驱动补充

当前又确认了一条更强的规则：

1. 是否需要鸡油、骨膏，不再靠口味名称猜
2. 是否需要去左上角，也不再靠文字判断
3. 一切以锅底配方接口返回的时长为准
4. 当鸡油时长或骨膏时长不为 `0` 时，该锅底必须走左上角辅料工位
5. 加水时长也同样来自锅底配方接口

## 10. 防飞溅补充规则

这是当前必须追加的一条现场约束：

1. 订单解析后，不论是单锅、拼锅还是四宫格，只要本轮涉及加水，所有需要加水的锅位都应统一启动加水。
2. 统一启动不代表统一停止，各锅位必须按照各自锅底配方时间独立停止。
3. 如果当前左上角锅位需要鸡油或骨膏，同时另一个非左上锅位也需要鸡油或骨膏，则非左上锅位不能在这一轮和左上角一起执行辅料。
4. 非左上锅位在这种场景下，连加水也必须延后，不能先参与统一加水。
5. 等当前左上角的鸡油/骨膏执行完成后，系统弹窗提示人工转锅。
6. 人工转锅确认完成后，再执行该非左上锅位的加水与鸡油/骨膏，并允许这三类动作在该相位内并行启动。
7. 这条规则不区分“单个辅料锅位”还是“多个辅料锅位”，只要某锅位需要辅料但不在左上角，都应优先先把其中一个转到左上角。
8. 当当前左上锅位同时需要鸡油和骨膏时，鸡油与骨膏允许同时开启。
9. 这条规则的目标是避免辅料动作在非目标工位并发时产生飞溅。
