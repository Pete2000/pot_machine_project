## 1. 当前版本目标

第一版 PLC 程序只要求稳定跑通下面三条执行线：

1. `PhaseExecutor`
   - 订单相位：4 路水、鸡油、骨膏
2. `HeaterController`
   - 主/备手动选择，本地回差控制
3. `EmergencyWaterExecutor`
   - 点动 / 时控独立补水

第一版先不做太复杂的自动恢复，不做太细的故障分层，不做自动转锅位置识别。

## 2. 基本控制原则

## 2.1 相位执行原则

1. `commandType = 1` 表示相位执行命令
2. 一条相位命令可以同时描述：
   - 4 路水
   - 当前左上锅位鸡油
   - 当前左上锅位骨膏
3. 水路统一启动、独立停止
4. 鸡油和骨膏允许同时开启
5. 一个相位里只能有一个 `activeTopLeftLogicalSlot`

## 2.2 加热原则

1. 上位机负责下发：
   - 设定温度
   - 温差
   - 主/备选择
   - 加热总使能
2. PLC 负责：
   - 回差控制
   - 主备互锁
   - 超低液位禁止加热
   - 急停禁止加热
   - 心跳超时撤销加热
3. 主、备加热绝对不能同时开启

## 2.3 应急补水原则

1. 应急补水是独立执行域
2. 与相位执行可以并行
3. 触摸屏模式切换：
   - `Jog`
   - `Timed`
4. 物理按钮含义：
   - `Jog` 模式：点动按钮
   - `Timed` 模式：启动按钮

## 2.4 异常原则

1. 安卓重启：
   - 当前订单视为未完成
   - 不标记成功
   - 由上位机重新开始
2. PLC 重启：
   - 所有输出安全关闭
   - 等待上位机重新下发
3. 心跳超时：
   - 加热撤销使能
   - 加热输出关闭

## 3. 命令协议定义

## 3.1 `commandType`

| 值 | 含义 |
| --- | --- |
| `0` | 空命令 |
| `1` | 相位执行命令 |
| `10` | 设置加热参数 |
| `11` | 加热开启请求 |
| `12` | 加热关闭请求 |
| `20` | 停止当前相位 |
| `30` | 故障复位 |

单位约定：

1. 所有相位时长按 `100ms` 为 1 个 tick
2. 例如：
   - `1.7s = 17`
   - `2.6s = 26`
   - `1.0s = 10`

## 3.3 加热命令字段

### `commandType = 10`

| 地址 | 字段 | 说明 |
| --- | --- | --- |
| `D300` | `commandId` | 命令号 |
| `D301` | `commandType` | 固定写 `10` |
| `D302` | `heaterSelect` | `1=主`，`2=备` |
| `D303` | `targetTemp` | 设定温度 |
| `D304` | `hysteresis` | 温差 |
| `D305` | `sensorSelect` | 预留，可写 `0` |

### `commandType = 11`

1. 只表示“允许加热”
2. 具体是否实际输出，由 PLC 根据回差和安全条件决定

### `commandType = 12`

1. 撤销加热使能
2. 强制关闭主备加热输出

## 4.5 历史直接写线圈区说明

你给的地址表里已经存在一套：

1. `M100 ~ M119`
2. 对应寄存器地址 `0x64 ~ 0x77`

这套更像“安卓直接写输出”的旧控制方式。

当前这版新架构建议：

1. `M100 ~ M119` 保留，不作为内部状态机主逻辑位
2. 订单相位、加热参数、停止、复位，统一走：
   - `D300 ~ D315`
3. PLC 实际执行输出仍然以：
   - `Y00 ~ Y23`
   为准
4. 安卓如果还要看执行结果，优先看：
   - `M320 ~ M339`
   - `D320 ~ D329`

这样可以做到：

1. 真实 PLC 程序按 `X/Y` 写
2. 上位机通讯按 `M300/M320/D300/D320` 对接
3. 内部状态机继续使用 `M500+ / D500+`

## 6. 主循环顺序

如果是 PLC 梯形图，建议按程序段顺序理解成一次扫描内的执行顺序：

1. 输入采集
2. 派生信号生成
3. 心跳与安全联锁
4. 命令邮箱处理
5. 相位执行
6. 加热控制
7. 应急补水
8. 输出互锁
9. 状态回写

建议注意：

1. 安全联锁一定在输出前起作用
2. 相位、加热、应急补水是三条并行执行域
3. 但都受统一安全位约束

## 12. 典型命令填写示例

这一节不是新增协议，而是把前面定义好的 `D300 ~ D315` 用实际例子填一遍。

### 12.1 四宫格相位命令示例

场景：

1. `1号位` 番茄锅，加水 `1.7s`
2. `2号位` 三鲜锅，加水 `2.6s`，鸡油 `1.0s`，骨膏 `1.4s`
3. `3号位` 清油锅，加水 `2.0s`
4. `4号位` 本相位不参与
5. 当前左上已经对应逻辑 `2号位`

约定：

1. 时间单位为 `100ms`
2. 所以：
   - `1.7s = 17`
   - `2.6s = 26`
   - `2.0s = 20`
   - `1.0s = 10`
   - `1.4s = 14`

则上位机写入：

| 地址 | 值 | 含义 |
| --- | --- | --- |
| `D300` | `1201` | `commandId` |
| `D301` | `1` | 相位执行命令 |
| `D302` | `7` | `jobSlotMask = 0b0111`，即 1/2/3 号位参与 |
| `D303` | `17` | 1 号位水时长 |
| `D304` | `26` | 2 号位水时长 |
| `D305` | `20` | 3 号位水时长 |
| `D306` | `0` | 4 号位本相位不参与 |
| `D307` | `2` | 当前左上逻辑锅位是 2 |
| `D308` | `10` | 鸡油时长 |
| `D309` | `14` | 骨膏时长 |
| `D310` | `1` | 第 1 相位 |

控制器锁存后应得到：

1. `D500 = 1201`
2. `D501 = 7`
3. `D502 = 17`
4. `D503 = 26`
5. `D504 = 20`
6. `D505 = 0`
7. `D506 = 2`
8. `D507 = 10`
9. `D508 = 14`
10. `D509 = 1`

随后运行变量应装载：

1. `D510 = 17`
2. `D511 = 26`
3. `D512 = 20`
4. `D513 = 0`
5. `D514 = 10`
6. `D515 = 14`

预期输出：

1. 起始时：
   - `M102/M103/M104 = ON`
   - `M105 = OFF`
   - `M109/M110 = ON`
2. 运行到 `10 tick`：
   - `M109 = OFF`
3. 运行到 `14 tick`：
   - `M110 = OFF`
4. 运行到 `17 tick`：
   - `M102 = OFF`
5. 运行到 `20 tick`：
   - `M104 = OFF`
6. 运行到 `26 tick`：
   - `M103 = OFF`
7. 全部结束后：
   - `D322 = 1201`
   - `D323 = 3`
   - `D324 = 0`

### 12.2 加热参数命令示例

场景：

1. 当前人工选中 `主加热`
2. 目标温度 `55`
3. 温差 `3`
4. 上位机准备允许 PLC 进入本地回差控制

先发参数命令：

| 地址 | 值 | 含义 |
| --- | --- | --- |
| `D300` | `2201` | `commandId` |
| `D301` | `10` | 设置加热参数 |
| `D302` | `1` | `1 = 主加热` |
| `D303` | `55` | 目标温度 |
| `D304` | `3` | 温差 |

控制器锁存后应得到：

1. `D530 = 1`
2. `D531 = 55`
3. `D532 = 3`
4. `D533 = 52`
5. `D534 = 58`

再发使能命令：

| 地址 | 值 | 含义 |
| --- | --- | --- |
| `D300` | `2202` | `commandId` |
| `D301` | `11` | 加热开启请求 |

控制器收到后：

1. 置位 `M535 = heater_request_enable`
2. 之后不再依赖上位机每次发“开/关”
3. 由本地回差逻辑决定：
   - `D200 <= D533` 时允许加热
   - `D200 >= D534` 时关闭加热
   - 中间保持

例如当前 `D200 = 50`，则：

1. `50 <= 52`
2. `M536 = heater_output_enable`
3. 若安全满足，输出：
   - `M100 = ON`
   - `M101 = OFF`

### 12.3 加热关闭命令示例

当上位机希望整体关闭加热时：

| 地址 | 值 | 含义 |
| --- | --- | --- |
| `D300` | `2203` | `commandId` |
| `D301` | `12` | 加热关闭请求 |

控制器应执行：

1. 复位 `M535`
2. 复位 `M536`
3. 强制：
   - `M100 = OFF`
   - `M101 = OFF`

### 12.4 应急补水时控示例

场景：

1. 触摸屏模式切到 `Timed`
2. 触摸屏设定补水时长 `3.0s`
3. 物理按钮在时控模式下作为“启动按钮”

内部量约定：

1. `D540 = 2`
2. `D541 = 30`

若本扫描检测到：

1. `M542 = emg_water_timed_mode`
2. `M548 = emg_water_btn_rising`
3. `M563 = 0`

则控制器应执行：

1. `S M544`
2. `MOV D541 -> D542`
3. 输出 `M107 = ON`
4. 之后每个 `100ms tick`：
   - `DEC D542`
5. 当 `D542 = 0`：
   - `R M544`
   - `S M545`
   - `M107 = OFF`

## 13. 执行完成判定规则

这一节的目的是把“什么时候算执行完成”定死，避免上位机和控制器理解不一致。

### 13.1 相位完成

一个相位命令只在下面 3 条同时满足时，才算真正完成：

1. `D322 == 当前 commandId`
2. `D323 == 3`
3. `D324 == 0`

控制器内部对应判定为：

1. `D510 ~ D515` 全部已经减到 `0`
2. `M514/M515/M516/M517/M519/M521` 已经全部置完成
3. `M508 = phase_all_done`

然后回写：

1. `D322 = latched_phase_command_id`
2. `D323 = 3`
3. `D324 = 0`

### 13.2 加热参数命令完成

`commandType = 10` 不是长事务。

控制器只要成功锁存参数并算出上下限，就可以回写完成：

1. `D320 = commandId`
2. `D321 = commandId`
3. `D322 = commandId`
4. `D323 = 3`
5. `D324 = 0`

### 13.3 加热使能命令完成

`commandType = 11` 的完成，不代表加热器此刻一定已经输出。

它只表示：

1. 控制器已经接受“允许加热”的请求
2. `M535 = heater_request_enable`
3. 后面是否真正输出，要继续看：
   - 温度条件
   - 液位
   - 急停
   - 故障
   - 心跳

所以对上位机要区分：

1. “使能命令成功”
2. “主加热器实际已经导通”
3. “备加热器实际已经导通”

实际导通请看：

1. `M320`
2. `M321`

### 13.4 应急补水完成

点动模式没有严格意义上的“事务完成”，更像实时控制：

1. 按下即运行
2. 松开即结束

时控模式的完成判定为：

1. `M544` 从 1 变 0
2. `D542 = 0`
3. `M545 = 1`

如果后面你希望把应急补水也纳入一套 `finishedCommandId` 回写体系，可以在第二版再加独立的应急补水命令区和状态区；第一版先不强求。
