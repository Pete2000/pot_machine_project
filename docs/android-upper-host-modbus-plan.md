## 1. 总体结论

对我们项目，最稳的安卓实现方式是：

1. **只保留一个 Modbus 串口收发线程**
   - `RS485 + Modbus RTU` 是半双工串行链路
   - 所有读写都必须串行排队
   - 不要为“相位 / 加热 / 应急补水”分别开独立串口线程
2. **在业务层可以有多个调度器**
   - 订单调度器
   - 相位调度器
   - 加热参数保存器
   - 手动模式控制器
   - 但它们最终都只往同一个 Modbus 队列里投任务
3. **安卓只负责业务规划和命令组织**
   - 订单解析
   - 配方匹配
   - 相位拆分
   - 转锅提示
   - 手动模式生成相位
4. **PLC/控制器负责实时执行和最终保护**
   - `PhaseExecutor`
   - `HeaterController`
   - `EmergencyWaterExecutor`
   - `LevelController`

一句话：

`安卓可以多协程/多模块，但真正的 Modbus 收发只走一个串口线程。`

## 2. 推荐线程 / 协程模型

## 2.1 必须有的线程

### A. `ModbusWorker`

职责：
1. 串口初始化
2. Modbus RTU 帧打包
3. 统一顺序读写
4. 超时重试
5. CRC 校验
6. 结果回调

要求：
1. 单线程
2. 队列化
3. 任何读写都不能绕过它直连串口

推荐实现：
1. Android `HandlerThread`
2. 或单独 `CoroutineScope + Channel`
3. 或单线程 `ExecutorService`

### B. `AppOrchestrator`

职责：
1. 订单 HTTP 轮询
2. 相位规划
3. 手动模式规划
4. 根据 PLC 状态推进下一步

它不直接碰串口，只调用 `ModbusWorker`。

### C. `Main/UI`

职责：
1. 展示 PLC 实际状态
2. 展示订单队列
3. 展示当前相位
4. 转锅弹窗
5. 手动界面

---

## 2.2 不建议的做法

不要这样做：

1. 一个线程专门读相位
2. 一个线程专门读加热
3. 一个线程专门写心跳
4. 一个线程专门写手动命令

原因：
1. 它们最终都会争同一个 `RS485` 通道
2. 容易出现帧交叉
3. 调试会很痛苦

## 3. Modbus 功能码总约定

根据《正电2N系列PLC MODBUS通信协议手册》，我们项目建议固定这样用：

## 3.1 M 区

1. 读 M 区：
   - 功能码 `01`
   - 读线圈/位
2. 写 M 区：
   - 单个位：功能码 `05`
   - 多个位：功能码 `15`

## 3.2 D 区

1. 读 D 区：
   - 功能码 `03`
   - 读保持寄存器
2. 写 D 区：
   - 单个寄存器：功能码 `06`
   - 多个寄存器：功能码 `16`

## 4. 地址换算基线

手册结论：

1. `M0 ~ M1535` 对应 Modbus 位地址 `0x0000 ~ 0x05FF`
2. `D0 ~ D511` 对应 Modbus 寄存器地址 `0x0000 ~ 0x01FF`

所以：

### 4.1 常用 M 地址

| 元件 | Modbus 地址 |
| --- | --- |
| `M300` | `0x012C` |
| `M320` | `0x0140` |
| `M339` | `0x0153` |
| `M400` | `0x0190` |
| `M500` | `0x01F4` |
| `M570` | `0x023A` |

### 4.2 常用 D 地址

| 元件 | Modbus 地址 |
| --- | --- |
| `D200` | `0x00C8` |
| `D210` | `0x00D2` |
| `D212` | `0x00D4` |
| `D214` | `0x00D6` |
| `D300` | `0x012C` |
| `D320` | `0x0140` |
| `D340` | `0x0154` |
| `D350` | `0x015E` |
| `D360` | `0x0168` |
| `D370` | `0x0172` |

注意：
1. `M300` 和 `D300` 的地址编号都可能显示为 `0x012C`
2. 它们不冲突，因为：
   - `M300` 走位/线圈功能码
   - `D300` 走寄存器功能码

## 5. 安卓上位机读写总表

## 5.1 固定轮询项

| 分类 | 读写 | 区域 | 功能码 | 起始地址 | 长度 | 建议周期 | 用途 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 输入/输出镜像 | 读 | `M300 ~ M339` | `01` | `0x012C` | `40` 位 | `200ms` | 按钮、输出状态、联调显示 |
| 相位状态 | 读 | `D320 ~ D329` | `03` | `0x0140` | `10` 寄存器 | `200ms` | `accepted/executing/finished`、相位状态 |
| 加热状态 | 读 | `D350 ~ D359` | `03` | `0x015E` | `10` 寄存器 | `500ms` | 加热状态、主备状态、参数回显 |
| 应急补水状态 | 读 | `D370 ~ D379` | `03` | `0x0172` | `10` 寄存器 | `200ms` | 点动/时控运行状态、备用泵状态 |
| 温度/液位 | 读 | `D200 ~ D214` | `03` | `0x00C8` | `15` 寄存器 | `500ms` | 温度、液位、辅助工艺寄存器 |

说明：
1. 如果实现时想减少帧数量，也可以把：
   - `D320 ~ D379`
   合并成一次 `03` 连续读，共 `60` 个寄存器
2. 第一版更推荐拆成：
   - `D320~D329`
   - `D350~D359`
   - `D370~D379`
   这样调试更直观

## 5.2 固定时间驱动项

| 分类 | 读写 | 区域 | 功能码 | 周期 | 用途 |
| --- | --- | --- | --- | --- | --- |
| 心跳 | 写 | `M400` | `05` | `1000ms` 翻转一次 | 通讯在线监测 |
| 订单 HTTP 拉取 | 读网络 | 订单接口 | HTTP | `1000~3000ms` 可配 | 接单 |
| 本地超时检查 | 本地定时 | 不走 Modbus | - | `200ms` | 相位超时、等待转锅超时、串口超时检查 |

建议：
1. `M400` 每秒在 `1/0` 间翻转
2. 不要用脉冲式“瞬间写1再写0”
3. 而是周期性写：
   - 第 1 秒：写 `1`
   - 第 2 秒：写 `0`
   - 第 3 秒：写 `1`

## 5.3 事件驱动写入项

| 场景 | 读写 | 区域 | 功能码 | 触发时机 |
| --- | --- | --- | --- | --- |
| 下发相位命令 | 写 | `D300 ~ D315` | `16` | 准备执行某一相位时 |
| 停止当前相位 | 写 | `D300 ~ D315` | `16` | 需要中止相位时 |
| 相位复位 | 写 | `D300 ~ D315` | `16` | 清故障/清状态时 |
| 保存加热参数 | 写 | `D340 ~ D349` | `16` | 加热参数页面点击保存 |
| 加热总使能 | 写 | `D340 ~ D349` | `16` | 上位机进入正常运行态时 |
| 关闭加热 | 写 | `D340 ~ D349` | `16` | 上位机停机/退出/关闭加热时 |
| 保存应急补水参数 | 写 | `D360 ~ D369` | `16` | 修改应急补水模式/时长/备用泵模式后 |

## 6. 相位、加热、应急补水、手动模式的安卓职责

## 6.1 相位相关

### 安卓负责
1. 订单解析
2. 配方查找
3. 规划总共有几个相位
4. 决定当前 `D302`
5. 决定当前 `D303 ~ D306`
6. 决定当前 `D307`
7. 决定当前 `D308 / D309`

### PLC 负责
1. 校验参数是否合法
2. 锁存本相位
3. 4 路同时启动、独立停止
4. 左上辅料执行
5. 回写相位完成状态

### 安卓触发方式
- **事件驱动**

即：
1. 当前相位准备好
2. 一次性写入 `D300 ~ D315`
3. 后续只轮询 `D320 ~ D329`

## 6.2 加热相关

### 安卓负责
1. 参数编辑
   - 主/备选择
   - 目标温度
   - 温差
2. 保存参数
3. 开启加热总使能
4. 关闭加热总使能

### PLC 负责
1. 本地回差控制
2. 超低液位/急停/故障/心跳超时保护
3. 主备互锁

### 安卓触发方式
- **参数保存：事件驱动**
- **加热总使能：状态驱动**
- **实时开关：不由安卓驱动**

结论：
1. 进入参数界面不发命令
2. 点击“保存”时发 `10`
3. 上位机进入正常运行时发 `11`
4. 上位机退出或关闭加热时发 `12`

## 6.3 单独应急补水相关

### 安卓负责
1. 画面切换：
   - `Jog`
   - `Timed`
2. 保存时控时长
3. 保存备用泵模式
4. 显示当前状态

### PLC 负责
1. 解释按钮在当前模式下的含义
2. 点动时按住开、松开关
3. 时控时按上升沿启动
4. 回写运行状态

### 安卓触发方式
- **参数部分：事件驱动**
- **状态部分：轮询**

所以：
1. `D360 ~ D369` 只在模式/参数变更时写
2. 真正按钮动作还是现场按钮 `X03`
3. 安卓只轮询 `D370 ~ D379`

## 6.4 手动选择锅型 / 锅底 / 手动加水模式

这块建议安卓单独做一个 **手动工艺模式**，但仍然不要绕开相位模型。

### 原则
1. 手动模式也尽量走“相位生成 -> 相位下发”
2. 不要在安卓里再搞一套完全不同的水路命令

### 推荐做法

#### A. 手动选择锅型 / 锅底
1. 选择锅型
   - 单锅 / 拼锅 / 四宫格
2. 选择锅底
3. 调配方接口
4. 生成一个“手动相位预览”

#### B. 手动“只加水”
如果用户只想试水、不加辅料：
1. 上位机生成一个相位命令
2. `D308 = 0`
3. `D309 = 0`
4. 只填需要测试的 `D303 ~ D306`

#### C. 手动“锅型 + 锅底 + 自动带辅料”
如果用户想按真实工艺手动跑：
1. 仍按配方生成相位
2. 如果锅底有鸡油/骨膏
3. 仍要遵守左上规则

## 8. 推荐安卓执行顺序

## 8.1 应用启动

1. 启动 `ModbusWorker`
2. 打开串口
3. 开始 `M400` 心跳
4. 读取基础状态：
   - `M300 ~ M339`
   - `D200 ~ D214`
   - `D320 ~ D379`
5. 如果进入正常运行态：
   - 先写加热参数 `D340 ~ D349`
   - 再下发加热总使能

## 8.2 正常接单

1. HTTP 拉单
2. 解析订单
3. 查配方
4. 规划相位队列
5. 下发第 1 相位
6. 轮询相位状态
7. 需要转锅就弹窗
8. 确认后下发下一相位
9. 全相位完成后，订单才算完成

## 8.3 手动模式

1. 人工选锅型 / 锅底
2. 本地生成相位预览
3. 点击执行时下发相位命令
4. 仍然按正常相位状态轮询

## 8.4 退出 / 异常

1. 发加热关闭
2. 停止订单推进
3. 心跳停止前先做收尾
4. 串口关闭

## 9. 我们项目最推荐的安卓模块划分

建议拆成：

1. `SerialPortManager`
   - 只管串口打开/关闭
2. `ModbusWorker`
   - 只管 Modbus 队列读写
3. `PlcPollingScheduler`
   - 只管轮询计划
4. `PhaseDispatchService`
   - 只管相位命令生成与推进
5. `HeaterConfigService`
   - 只管加热参数/使能
6. `EmergencyWaterConfigService`
   - 只管应急补水参数和备用泵模式
7. `ManualModeService`
   - 只管手动锅型/锅底/测试执行
8. `OrderRuntimeService`
   - 订单、配方、相位全局协同

核心原则：

`业务模块可以分很多个，但真正进串口的入口只有 ModbusWorker 一个。`

---

## 10. 最终建议

如果我们现在开始落安卓实现，我建议按下面顺序做：

1. 先做 `ModbusWorker`
2. 再做固定轮询
3. 再做相位下发
4. 再做加热参数保存和 `11/12`
5. 再做应急补水参数页面
6. 最后做手动锅型/锅底模式

这样风险最低，最容易联调。

## 11. 安卓上位机通信配置项清单

这部分建议做成“设备通信设置”页面，并本地持久化。

原则：
1. **通信层参数可配置**
2. **协议语义不可配置**
3. 修改后先做一次连接测试，再正式生效

## 11.1 建议开放配置的项目

| 配置项 | 建议默认值 | 是否建议开放 | 说明 |
| --- | --- | --- | --- |
| 串口设备路径 / 串口号 | 依设备而定 | 是 | 例如 `/dev/ttyS*`、`/dev/ttyUSB*` 或厂商串口名 |
| 波特率 | `19200` | 是 | 我们当前项目默认值 |
| 数据位 | `8` | 是 | 默认 `8` |
| 校验位 | `None` | 是 | 默认无校验 |
| 停止位 | `1` | 是 | 默认 `1` |
| PLC 从站地址 | `1` | 是 | Modbus slave id |
| 读超时 | `500ms` | 是 | 单次读帧超时 |
| 写超时 | `500ms` | 是 | 单次写帧超时 |
| 重试次数 | `1` 或 `2` | 是 | 串口波动时可重试 |
| 心跳周期 | `1000ms` | 是 | `M400` 翻转周期 |
| 运行中轮询周期 | `200ms` | 是 | 运行相位时使用 |
| 空闲轮询周期 | `500ms` | 是 | 无活跃相位时使用 |
| HTTP 拉单周期 | `1000~3000ms` | 是 | 订单接口轮询周期 |
| 连接测试目标寄存器 | `D200` 或 `D320` | 是 | 保存配置后做读测试 |

## 11.2 不建议做成配置项的内容

这些应该固定在代码和正式协议里，不建议在 UI 上开放：

| 项目 | 原因 |
| --- | --- |
| `M300 ~ M339`、`D300 ~ D379` 地址定义 | 属于协议语义，不该让现场改 |
| `commandType` 含义 | 属于上下位机协议，不该配置化 |
| 相位字段结构 | 属于业务协议，不该配置化 |
| `M400` 作为心跳位 | 可以改周期，但不建议改心跳地址 |
| `D302~D310` 字段含义 | 必须固定，否则相位命令会失真 |

## 11.3 推荐配置数据结构

建议安卓侧至少持久化这些字段：

```text

baudRate
dataBits
parity
stopBits
slaveId
readTimeoutMs
writeTimeoutMs
retryCount
heartbeatPeriodMs
pollingActiveMs
pollingIdleMs

testRegisterAddress
```

## 11.4 推荐 UI 行为

通信设置页建议这样做：

1. 进入页面时显示当前生效配置
2. 用户修改后点击“保存”
3. 先不立刻覆盖运行中的通信配置
4. 先执行一次“连接测试”
5. 测试成功后：
   - 保存本地配置
   - 关闭旧串口
   - 重建 `ModbusWorker`
   - 重新启动轮询和心跳
6. 测试失败后：
   - 保持旧配置继续运行
   - 给出错误提示

## 11.5 推荐“连接测试”步骤

保存配置时建议做一次轻量测试：

1. 用新配置重新初始化串口
2. 读取一个稳定寄存器区
   - 推荐 `D200 ~ D210`
   - 或 `D320 ~ D329`
3. 如果：
   - CRC 正确
   - 从站响应正常
   - 数据长度正常
   则判定测试成功

推荐测试顺序：
1. 先读 `D200 ~ D214`
2. 再读 `M300 ~ M339`

## 11.8 最终建议

一句话总结：

`串口、波特率、站号、超时、轮询周期这些做成可配置是对的；地址映射和协议字段不要做成可配置。`
