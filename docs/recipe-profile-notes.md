# 锅底配方接口说明

## 1. 当前确认的规则

锅底的实际执行参数，不应从订单文字直接判断，而应从锅底配方接口取得。

当前已经明确：

1. 锅底通过 `potBottomId` 或锅底编码映射到锅底配方
2. 锅底配方至少要能返回
   `加水时长`
   `鸡油时长`
   `骨膏时长`
3. 当 `鸡油时长 > 0` 或 `骨膏时长 > 0` 时，这个锅底必须去左上角辅料工位执行
4. 当辅料时长为 `0` 时，这个锅底不需要为了辅料专门去左上角

## 2. 对终端的影响

终端执行链路应该变成：

`订单接口 -> parentId 还原锅底树 -> 锅底ID -> 配方接口 -> 生成控制计划`

也就是说：

1. 订单接口负责告诉我们锅型、锅底、口味、备注、锅位关系
2. 配方接口负责告诉我们每个锅底在指定锅型下到底要加多少水、鸡油、骨膏
3. 控制计划只认配方结果，不认模糊文案

## 3. 当前代码里的落点

代码里已经补了这层模型：

1. `PotRecipeProfile`
2. `PotFlavor.recipeProfile`
3. `DispatchStep.durationMs`
4. `PotOrderParser.parse(lines, recipeProfilesByPotBottomId)`

也就是后面只要把锅底配方接口接进来，订单解析就能直接带着配方生成执行计划。

## 3.1 从真实样例确认到的新信息

你提供的真实返回又确认了几件关键事：

1. 配方不是只按锅底查，还和 `potTypeCode` 强相关
2. 同一个 `potCode` 在
   `单锅 / 拼锅 / 四宫格`
   下的 `addWater/addChickenOil/boneOil` 都可能不同
3. 返回里存在多个 `formulaCode`
4. 返回里存在 `whetherDefault`
5. 这意味着终端最终取配方时，至少要按
   `potCode + potTypeCode`
   做匹配
6. 当前真实接口调用方式应以 `POST + x-www-form-urlencoded` 为准
7. 还需要明确多个 `formulaCode` 同时返回时的选用优先级

## 3.2 当前真实样例里的重要发现

1. `三鲜火锅`
   在不同锅型下确实存在不同的 `addWater/addChickenOil/boneOil`
2. `单锅` 的 `三鲜火锅` 有 `boneOil = 5.00`
3. `拼锅` 的 `三鲜火锅` 有 `addChickenOil = 1.00` 且 `boneOil = 2.80`
4. `四宫格` 的 `三鲜火锅` 有 `boneOil = 1.40`
5. 这直接证明“是否去左上角”和“加料时长”必须由配方接口决定

## 4. 配方接口还需要你们确认的内容

1. 配方接口地址
2. 请求方式
3. 请求参数
   是单个锅底查询，还是批量锅底查询
4. 返回字段名
   尤其是加水、鸡油、骨膏时长字段
5. 时长单位
   毫秒、秒，还是 PLC 脉冲计时单位
6. 是否还有其他配料口
7. 是否存在同一锅底在不同门店、不同设备上的不同配方
8. 当多个 `formulaCode` 同时返回时，终端应该如何选择
