## 1. 当前确认

1. 现场形态是同一台安卓主机外接第二显示器，第二显示器带触摸。
2. 主屏仍然是唯一上位控制台，负责 PLC 控制、相位推进、人工转锅提示、设置和维护。
3. 副屏不是第二个主控台，只是“传锅工作台”。
4. 副屏允许的能力当前限定为：
   - 查看待传锅订单
   - 查看已完成订单
   - 点击传锅完成
5. 副屏不负责：
   - 发起加水
   - 推进下一相位
   - 处理人工转锅
   - 修改配方或设备设置
   - 直接下发 PLC 控制命令

## 2. 先区分两种“传锅”

当前必须明确区分下面两件事，不能混用：

1. 人工转锅
   - 这是机内流程的一部分
   - 目的是把需要辅料的锅位转到左上工位
   - 属于主屏控制流程
   - 不进入副屏待传锅列表

2. 待传锅
   - 这是某个订单在当前工位已经做完，等待去下一个环节
   - 这时订单才应进入副屏
   - 副屏的“传锅完成”确认的是这一步

结论：
`人工转锅 != 待传锅`

## 3. 待传锅的进入时机

待传锅不能由“点了加水按钮”直接触发，也不建议由“某一路阀门先关了”直接触发。

当前建议采用“本工位最后一个相位完成”作为唯一触发条件。

对单个相位完成的判定，按已有握手草案执行：

1. `finishedCommandId == 当前 commandId`
2. `plcActionState == Completed`
3. `resultCode == 0`

只有三者同时满足，才认为当前相位真正完成。

随后由上位机判断：

1. 当前订单是否还有下一相位
2. 是否还存在人工转锅步骤
3. 当前是否已经是该订单在本工位的最后一个相位

只有“最后一个相位完成”时，才把订单迁移到 `WaitingTransfer`。

## 4. 双屏的核心原则

双屏设计当前采用下面 4 条铁律：

1. 不做整屏互锁
   - 任何一块屏操作时，另一块屏都不应表现得像死机
2. 读操作尽量永远可用
   - 查看待传锅
   - 查看已完成
   - 滚动列表
3. 写操作按对象串行，不按整屏串行
   - 同一张订单的冲突需要控制
   - 不同订单之间尽量不要互相阻塞
4. PLC 写通道和订单状态写通道分开
   - 主屏加水属于 PLC 写操作
   - 副屏传锅完成属于订单状态写操作
   - 两者不能共用一把“大锁”

## 5. 主副屏职责边界

### 主屏

1. 接单和队列调度
2. 生成相位
3. 下发 PLC 相位命令
4. 轮询 PLC 状态区
5. 判定相位完成和订单完成
6. 人工转锅提示与确认
7. 设备设置和维护操作

### 副屏

1. 展示 `WaitingTransfer` 队列
2. 展示 `Completed` 队列
3. 对已进入 `WaitingTransfer` 的订单执行“传锅完成”

副屏上的“传锅完成”不直接写 PLC，只改订单状态，并可异步回传后端。

## 6. 主屏加水是否影响副屏传锅

当前基线结论：

`主屏加水不应影响副屏传锅。`

前提是：

1. 主屏加水走 PLC 命令通道
2. 副屏传锅完成只走订单状态更新通道
3. 副屏传锅完成不参与 PLC 命令锁

只有下面两类场景，副屏的“传锅完成”才应被限制：

1. 同一张订单冲突
   - 该订单尚未真正进入 `WaitingTransfer`
   - 或该订单当前正在主屏执行状态迁移
2. 关键维护态
   - 主屏正在重连 PLC
   - 主屏正在切换 PLC 通讯参数
   - 主屏正在清运行队列或重建运行态

除这两类场景外，主屏加水与副屏传锅应并行存在。

## 6.1 物理按钮 `M302` 是否可作为传锅完成来源

当前建议：

`可以使用 M302 作为传锅完成的输入来源，但不能把“读到 1”直接等价成“订单完成传锅”。`

原因不是点位本身有问题，而是“事件解释”如果过于简单，会产生误判和重复触发。

### 可以成立的前提

1. `M302` 确实对应现场的“传锅完成”物理按钮
2. 上位机持续轮询 PLC 输入点
3. 现场在任一时刻，传锅工位只会确认一张“当前待传锅订单”

### 不能直接写成 `if (M302 == 1) 完成订单` 的原因

1. 轮询读到的是电平，不是天然的一次性事件
   - 只要按钮保持按下，连续多次轮询都会读到 `1`
   - 如果没有额外处理，同一张订单可能被重复完成
2. 单个输入点本身不携带订单标识
   - `M302` 只能说明“有人按了传锅完成”
   - 不能天然说明“完成的是哪一张订单”
3. 可能存在抖动或误触
   - 机械按钮可能在短时间内抖动
   - 不能把瞬时毛刺直接当成有效业务提交

### 正确解释方式

`M302` 应被解释成“传锅确认事件源”，而不是“订单主键”。

上位机需要把这个事件映射到“当前可确认的那一张待传锅订单”。

建议规则：

1. 只在 `WaitingTransfer` 队列非空时监听 `M302`
2. 只对“当前激活的待传锅订单”生效
3. 优先完成副屏当前选中订单
4. 如果副屏没有选中，则完成队列头部订单
5. 如果当前没有明确唯一目标订单，则忽略本次按键并提示

### 必须做的防重处理

建议最少做下面 3 件事：

1. 上升沿触发
   - 只把 `0 -> 1` 当成一次有效确认
   - `1 -> 1` 不重复触发
2. 释放后再允许下一次
   - 必须等按钮回到 `0`
   - 下一次 `0 -> 1` 才算新事件
3. 幂等校验
   - 目标订单已经不是 `WaitingTransfer` 时，忽略这次确认

### 推荐状态机

可按下面理解：

1. 轮询读 `M302`
2. 如果当前值为 `1` 且上一次值为 `0`
   - 生成一次 `PhysicalTransferConfirmPressed` 事件
3. 协调器查找当前唯一可确认订单
4. 若找到订单且该订单状态为 `WaitingTransfer`
   - 执行 `ConfirmTransfer(orderId, source = PhysicalButton)`
5. 若无唯一目标订单
   - 不提交订单完成
   - 只做日志和 UI 提示

### 与副屏按钮的关系

当前推荐把下面两个来源统一收口到同一个业务入口：

1. 副屏触摸点击“传锅完成”
2. 物理按钮 `M302`

也就是两者最终都进入同一个协调器意图：

`ConfirmTransfer(orderId, source = SecondaryDisplay | PhysicalButton)`

这样才能保证：

1. 幂等规则一致
2. 订单锁一致
3. 日志审计一致
4. 不会因为来源不同而出现两套状态机

### 当前应避免的做法

1. 读到 `M302 == 1` 就直接把队列里所有待传锅订单都完成
2. 读到 `M302 == 1` 就绕过协调器直接改状态
3. 副屏按钮走一套逻辑，物理按钮再走另一套逻辑
4. 不做上升沿检测，导致长按完成多单
5. 在没有明确目标订单时仍然强行完成队列头，造成串单

## 6.2 副屏五卡片布局与物理按键目标位

当前新增确认：

1. 副屏计划同时展示 5 个待传锅订单
2. 布局为“上三、下二”
3. 卡位编号按固定物理位置定义，不按普通阅读顺序定义
4. 物理按键 `M302` 永远只对“左下卡片”生效

这套方案可以成立，但必须把“左下卡片”定义成固定的业务概念，而不是普通排版结果。

当前建议把左下卡片定义为：

`Confirm Slot`

也就是：

1. 左下卡片不是普通展示位
2. 左下卡片是“当前物理按键确认目标位”
3. `M302` 的上升沿事件只会确认绑定在这个位置上的订单

### 推荐卡片位定义

当前以你确认的草图为准：

```text
3   2   1

5       4
```

卡位编号固定定义为：

1. `card1` = 右上
2. `card2` = 上中
3. `card3` = 左上
4. `card4` = 右下
5. `card5` = 左下，物理确认位

### 关键规则

1. 任意时刻，只有 `card5` 与物理按键绑定
2. 物理按键不直接绑定“最新订单”或“最早订单”这个抽象规则
3. 物理按键绑定的是“当前被放入 `card5` 的订单”
4. 队列选择策略只决定“谁被放进 `card5`”

这样做的好处是：

1. 物理按键目标永远清楚
2. UI 和按键行为完全一致
3. 后续要切“最新优先”或“最早优先”时，只需要替换 `card5` 选单规则

## 6.3 `card5` 选单策略

当前你提出的两个候选策略都可以：

1. 最早待传锅订单优先
2. 最新待传锅订单优先

这两种都能做，但生产环境建议尽量固定，不建议让操作员频繁切换。

原因：

1. 物理按钮没有屏幕上下文
2. 操作员按按钮时，依赖的是肌肉记忆和视觉直觉
3. 如果系统一会儿按最早，一会儿按最新，容易造成“我以为完成的是 A，结果系统完成了 B”

当前推荐优先级：

1. 固定“最早待传锅优先”
2. 如果现场流程必须追新，再评估“最新待传锅优先”
3. 不建议把“最早/最新切换”做成高频操作

推荐“最早优先”的原因：

1. 更接近 FIFO 队列直觉
2. 更容易避免老订单滞留
3. 更适合物理按钮这种低语义输入
4. 更容易与“左下确认位递补路径”保持一致

### 如果必须支持切换

当前新增确认：

1. 系统允许保留“左下最老 / 左下最新”切换能力
2. 默认模式必须是“左下最老”
3. 切换权限必须受管理员权限控制

那也必须满足下面要求：

1. 当前模式要长期固定，不应让传锅员临时频繁切
2. 副屏顶部要明确显示：
   - `当前确认模式：最早优先`
   - 或 `当前确认模式：最新优先`
3. 左下卡片要有明显标识：
   - `物理按键确认位`
4. `M302` 日志里要记录：
   - 触发时模式
   - 目标订单 id
5. 只有管理员才能修改该模式
6. 建议该模式写入系统配置并持久化
7. 建议切换时弹出二次确认，明确告知“将改变左下物理确认位的取单规则”
8. 建议切换动作本身记录审计日志

### 切换能力的定位

这项切换能力不是常规生产操作，而是“受限的现场兜底能力”。

当前新增理解：

“左下最新”不一定表示现场要优先传新锅，它更多是给现场一个容错口子：

1. 传锅员可能已经按真实流程把锅传走
2. 但当下没有及时做“传锅完成”确认
3. 系统里会积压一批尚未确认的 `WaitingTransfer`
4. 如果仍严格按“左下最老”显示，左下确认位会长期被这些未确认旧单占住
5. 后续传锅员即使只是想看当前屏幕，也可能看不到最接近现场真实状态的新单

所以当前建议这样理解：

1. 正常模式始终使用“左下最老”
2. “左下最新”只是管理员授权下的特殊工作模式
3. 它的存在主要是为了应对“现场已传锅但未及时确认，导致旧待传锅积压遮挡当前信息”的情况
4. 不能把它当成传锅员日常自己切换的按钮
5. 它是容错模式，不是常规调度模式

## 6.4 渲染规则建议

为了避免“订单少的时候左下没卡”或“物理按键目标位置漂移”，副屏不能按普通瀑布流方式排卡。

应采用下面规则：

1. 队列不是普通二维网格，而是一条固定推进路径
2. `slot4` 是路径终点，也是物理确认位
3. 新订单进入路径起点
4. 订单完成后，后面的卡片沿路径依次递补

当前建议不要再用“slot 路径”描述，而是直接用固定确认序列描述：

`5、4、3、2、1`

含义是：

1. `card5` 左下是第一确认位，也是当前物理按键确认目标
2. `card4` 右下是第二确认位
3. `card3` 左上是第三确认位
4. `card2` 上中是第四确认位
5. `card1` 右上是第五确认位

## 6.4.1 递补规则

当 `card5` 订单被确认完成后，副屏按下面顺序递补：

1. `card4 -> card5`
2. `card3 -> card4`
3. `card2 -> card3`
4. `card1 -> card2`
5. 队列中的下一张新订单 -> `card1`

这就是当前确认的“右下补左下，上排再依次递补”规则。

如果可用订单不足 5 张，则只移动当前存在的卡片：

1. 若 `card4` 为空，则 `card5` 补空
2. 若 `card3` 有卡而 `card4` 空，则 `card3` 直接补到 `card4`
3. 其余位置继续按同一路径收缩

结论：

1. 页面上不能出现中间空洞不补
2. `card5` 应尽量始终有卡
3. 副屏布局必须由“队列路径”驱动，而不是由普通列表渲染驱动

## 6.4.2 队列语义

一旦采用上面的递补路径，当前建议不要再做“最新优先 / 最早优先”高频切换。

原因：

1. 路径本身已经编码了队列先后关系
2. `card5` 是当前最应被确认的订单
3. `card4` 是下一个最应被确认的订单
4. `card1` 是离确认最远、最新进入路径的订单

所以当前更推荐直接固定为 FIFO 语义：

1. 最老的待传锅订单在 `card5`
2. 次老的在 `card4`
3. 再往后依次是 `card3`
4. 再往后是 `card2`
5. 最新进入的是 `card1`

这样操作员对物理按钮的心理模型会非常稳定。

如果管理员切到“左下最新”，则应同步切换整条路径的理解方式，保证左下仍然是“当前确认位”，只是当前确认位绑定的是最新目标而不是最老目标。

当前仍建议：

1. 默认模式长期保持 FIFO
2. 非必要不切到“左下最新”
3. “左下最新”开启时，系统必须明确告知：当前处于容错显示模式，队列中可能存在待补确认旧单

### 两种模式的卡位映射

#### 默认模式：左下最老

固定确认序列仍然是 `5、4、3、2、1`，只是填充内容按“从老到新”映射：

1. `card5` = 最老
2. `card4` = 次老
3. `card3` = 第三老
4. `card2` = 第四老
5. `card1` = 第五老

#### 容错模式：左下最新

固定确认序列仍然是 `5、4、3、2、1`，只是填充内容按“从新到老”映射：

1. `card5` = 最新
2. `card4` = 次新
3. `card3` = 第三新
4. `card2` = 第四新
5. `card1` = 第五新

## 6.4.3 容错模式下的积压订单

如果开启“左下最新”，系统必须承认一个事实：

1. 队列前部可能存在尚未确认但现场实际上已经传走的旧订单
2. 这些订单不能因为切到“左下最新”就被自动完成
3. 它们应继续保留在系统中，但要被标记为“待补确认”

当前建议：

1. 默认模式下，旧订单按 FIFO 正常推进
2. 容错模式下，左下优先展示最新订单，方便现场继续看当前单
3. 但系统同时要显示：
   - `待补确认 X 单`
   - 或 `存在未确认旧单`
4. 管理员在合适时机切回默认模式，或通过补确认流程清理旧积压

当前应避免：

1. 一切到“左下最新”就把旧单从系统里隐藏掉
2. 一切到“左下最新”就默认认为旧单已经完成
3. 让操作员误以为最新模式下不再需要做确认闭环

## 6.5 `M302` 的最终确认流程

结合五卡片布局，推荐流程如下：

1. 上位机轮询 `M302`
2. 检测到 `0 -> 1`
3. 读取当前 `card5` 绑定的订单 `confirmOrder`
4. 若 `confirmOrder` 存在且状态为 `WaitingTransfer`
   - 执行 `ConfirmTransfer(confirmOrder.id, source = PhysicalButton)`
   - 完成后按递补规则刷新 5 个卡位
5. 若 `card5` 当前无订单
   - 忽略本次物理按键
   - 只做日志

## 6.6 当前推荐结论

1. “上三下二 + 左下固定物理确认位 + 递补路径”是可行方案
2. 左下必须是业务上的固定确认位，不能只是视觉上的一个格子
3. `M302` 永远确认左下卡片，比“直接确认最新单/最早单”更稳
4. 左下完成后，必须按 `4 -> 5、3 -> 4、2 -> 3、1 -> 2` 的固定递补顺序补位
5. 默认采用 FIFO，也就是“左下最老”
6. 如需“左下最新”，只允许管理员切换
7. 切换能力属于受限兜底能力，不属于传锅员常规操作
8. “左下最新”的主要目的，是在旧待传锅未及时确认时，给现场继续看当前单留一个活口
9. 开启该模式时，必须同时暴露“待补确认旧单”的存在，不能假装系统状态完全正确

## 6.7 副屏展示补充

当前新增确认的副屏展示方案：

1. 固定 5 张大卡片
2. 左下为物理确认位
3. 显示待传锅总数
4. 显示第 6 单预告

推荐展示内容：

1. 待传锅总数
2. 当前确认模式
3. 第 6 单预告：
   - 桌号
   - 锅型
   - 锅底名称

第 6 单预告的目标是避免队列超过 5 单时，后续操作员完全不知道自己订单是否已进入待传锅队列。

## 7. 设置操作的影响范围

为了避免“主屏进设置页，副屏像死机”，当前建议把设置分成两类。

### 普通业务设置

特点：

1. 不直接影响当前 PLC 运行链路
2. 允许只作用于后续新订单
3. 不应阻塞副屏传锅

示例：

1. 页面展示项
2. 排序和筛选偏好
3. 普通业务文案
4. 仅影响后续订单解析的业务开关

规则：

1. 主屏进入设置页时，副屏不受影响
2. 主屏编辑草稿时，副屏不受影响
3. 主屏保存普通业务设置时，副屏仍可继续传锅
4. 已进入 `WaitingTransfer` 的订单不受这类设置回写影响

### 关键设备设置

特点：

1. 会影响当前设备运行链路
2. 可能影响 PLC 连接或队列一致性
3. 允许短时进入维护态

示例：

1. PLC 串口参数
2. 从站地址
3. 设备码或接口地址
4. 运行队列重建
5. 清队列
6. 控制流程重置

规则：

1. 进入“编辑页面”时不锁副屏
2. 只有点击“应用/保存”且真正提交时，才进入维护态
3. 维护态期间，副屏保留只读
4. 维护态期间，只暂停副屏的“传锅完成”
5. 副屏的待传锅和已完成列表仍允许查看和滚动

## 8. 锁模型建议

当前建议只保留 3 类锁。

### `plcCommandLock`

用途：

1. 串行化 PLC 命令下发
2. 保护相位命令、停止命令、重连等设备写操作

谁会使用：

1. 主屏发起加水/相位执行
2. 主屏停止当前动作
3. 主屏关键维护动作

副屏不应使用这把锁。

### `orderLock(orderId)`

用途：

1. 保护同一张订单的状态迁移
2. 避免同一张订单被主副屏同时推进

谁会使用：

1. 主屏把订单迁移到 `WaitingTransfer`
2. 副屏执行“传锅完成”
3. 主屏取消、修正或刷新该订单状态

这把锁是“按订单局部生效”，不能升级成整屏锁。

### `maintenanceLock`

用途：

1. 表示系统处于关键维护态
2. 暂停有限的写操作

谁会使用：

1. 主屏应用关键设备设置
2. 主屏重连 PLC
3. 主屏重建运行态

维护态期间：

1. 副屏仍可查看列表
2. 副屏“传锅完成”按钮置灰
3. 不能整页无响应

## 9. 典型操作矩阵

| 操作 | 所在屏幕 | 写入目标 | 需要的锁 | 对另一块屏的影响 |
| --- | --- | --- | --- | --- |
| 查看待传锅/已完成 | 主屏/副屏 | 无 | 无 | 无影响 |
| 主屏发起加水或相位执行 | 主屏 | PLC | `plcCommandLock` + 当前订单 `orderLock` | 不应阻塞副屏对其他订单的传锅 |
| 主屏轮询 PLC 完成并迁移到 `WaitingTransfer` | 主屏 | 订单状态 | 当前订单 `orderLock` | 只影响同一订单卡片刷新 |
| 副屏点击传锅完成 | 副屏 | 订单状态 | 当前订单 `orderLock` | 不应阻塞主屏的 PLC 操作 |
| 主屏浏览设置页或编辑草稿 | 主屏 | 无或草稿态 | 无 | 不应影响副屏 |
| 主屏保存普通业务设置 | 主屏 | 配置存储 | 可选轻量配置锁 | 不应影响副屏传锅 |
| 主屏应用关键设备设置 | 主屏 | 设备运行态 | `maintenanceLock` + 视情况使用 `plcCommandLock` | 副屏进入只读，暂停传锅完成 |

## 10. UI 交互要求

为了避免被误判为“死机”，双屏 UI 必须满足下面要求。

1. 不允许整页静默失效
2. 不允许一个按钮点不动但没有原因
3. 任何受限状态都必须显示明确文案
4. 加载或提交中的视觉反馈只作用于当前卡片或当前按钮

推荐表现：

1. 主屏正在提交关键设备设置时
   - 副屏顶部提示：`设备维护中，传锅确认已暂停`
2. 某张订单正在被主屏迁移状态时
   - 副屏这张订单的“传锅完成”按钮置灰
   - 文案提示：`该订单正在处理中`
3. 副屏提交传锅完成时
   - 只让该卡片显示 loading
   - 其他卡片仍可查看和操作

## 11. 实现建议

当前项目后续改造时，建议把双屏能力落在下面结构上。

1. 增加应用级共享状态仓库，例如 `MachineRuntimeStore`
2. 增加应用级协调器，例如 `MachineCoordinator`
3. 主屏与副屏都只读共享状态，不直接各自修改订单真相
4. 所有写操作都改为向协调器发送意图
5. 协调器内部按锁模型串行化

建议的意图示例：

1. `StartPhase(orderId, commandId)`
2. `PhaseCompleted(commandId)`
3. `MoveToWaitingTransfer(orderId)`
4. `ConfirmTransfer(orderId, source = SecondaryDisplay)`
5. `ApplyCriticalDeviceSettings`

Android 层建议：

1. 主屏使用主 Activity
2. 副屏使用独立的 `SecondaryTransferActivity`
3. 通过 `DisplayManager` 发现第二显示器
4. 通过 `launchDisplayId` 把副屏 Activity 启到第二显示器

## 12. 现场验证清单

这部分很关键，因为第二显示器带触摸，问题不一定全部来自 App。

上线前至少验证下面事项：

1. 第二显示器能否被 Android 正确识别为独立显示器
2. 第二显示器的触摸是否正确路由到第二显示器，而不是主屏
3. 主副屏能否同时各自接收点击
4. 副屏的触摸是否会抢掉主屏焦点
5. 主屏进入全屏沉浸模式时，副屏是否仍可正常触摸
6. 主屏执行 PLC 命令时，副屏是否仍可滚动列表
7. 副屏连续点两次“传锅完成”时，是否能正确幂等
8. 主屏应用关键设备设置时，副屏是否仅暂停写操作而不是整页假死

## 13. 当前应遵守的落地结论

为避免后续实现跑偏，当前先固化下面结论：

1. 副屏只做“待传锅 + 已完成 + 传锅完成”
2. 主屏加水不应阻塞副屏传锅
3. 副屏传锅完成不直接写 PLC
4. 不做整屏互锁，只做同订单冲突控制
5. 主屏进设置页不影响副屏
6. 只有关键设备设置提交时，副屏才进入只读
7. 任何限制都必须有明确 UI 提示，不能让操作员误以为系统死机
