# 打锅机 POS 订单与状态协同架构设计文档

> [!IMPORTANT]
> 本文档定义了 Android 上位机与云端 POS 系统进行订单数据同步、解析及生命周期管理的核心规范。由于 POS 接口具有极强的“操作流”特性，本架构以**防丢单、防重复、物理状态唯一**为最高设计准则。

## 1. 核心架构原则

1.  **本地状态优先原则 (Local Status Priority)**
    上位机（Android）仅负责排队与下发，**下位机（PLC/MCU）是物理状态的唯一真理**。一旦锅底任务在本地进入 `RUNNING`（制作中）或 `COMPLETED`（已完成）状态，无论是轮询延迟还是网络波动带来的旧数据，都**绝不允许**覆盖或逆转本地状态。
2.  **事件流驱动 (Event Stream Driven)**
    API 返回的报文并非当前订单的绝对快照，而是基于时间轴的**操作流水日志**。同一口锅在生命周期内会因不同操作（加单、退菜、换桌）产生多条关联数据。
3.  **实体 ID 与事件 ID 分离**
    301 根记录 `id` 是订单实体主键；302/303/304 的根 `id` 是事件幂等 ID，不能替换实体主键。`baseHash` 只用于跨事件关联。同账单、同锅型、同锅底顺序仍可能是两口真实锅，不能用内容指纹合并。

## 2. 订单树状重构模型

接口数据由扁平的 JSON 数组构成。必须通过 `id` 与 `parentId` 重新组装为**任务树**，每一棵完整的树代表物理世界中的“一口锅”。

### 2.1 层级解析逻辑
*   **根节点（Level 0 - 实体锅）**
    特征：`parentId == null`。例如：“四宫格”、“拼锅”、“大锅”。它定义了物理锅的容量和分区。
*   **子节点（Level 1 - 汤底实体）**
    特征：`parentId` 指向根节点的 `id`。带有 `potSort` 属性（如 1, 2, 3, 4），决定该汤底打入机器的几号工位。例如：“清油麻辣火锅”、“番茄锅”。
*   **孙节点（Level 2 - 口味修饰符）**
    特征：`parentId` 指向子节点的 `id`。例如：“无渣”、“加麻加辣”、“不要姜”。此节点属于控制指令，直接影响对应工位的加料逻辑。

### 2.2 锅型与锅底完整性校验

订单解析不能只依赖“能解析出几个锅底就显示几个锅底”。每一棵锅型任务树在进入 UI 展示、配方匹配、相位规划和 PLC 下发前，必须先完成结构完整性校验。

#### 2.2.1 单一事实源

1. 锅底顺序以接口原始 JSON 数组顺序为准，不使用 `potSort` 排序。
2. `potSort` 仅允许作为调试参考字段，不参与锅位落位、不参与 `Base_Hash`、不参与 UI 展示顺序。
3. 锅型根节点决定期望锅底数量，锅底子节点决定实际锅底数量。

#### 2.2.2 期望数量

| 锅型 | 期望锅底数 | UI 物理展示位 |
| --- | ---: | --- |
| 单锅 / 小锅 | 1 | 整锅或左上 |
| 拼锅 | 2 | 左侧、右侧 |
| 三拼锅 / 三宫格 | 3 | 左上、右上、下方 |
| 四宫格 | 4 | 左上、右上、左下、右下 |

#### 2.2.3 校验输入

解析器至少要记录以下数量，用来判断是“接口缺失”还是“解析漏了”：

1. `expectedSlotCount`：由锅型推断出的期望锅底数。
2. `attachedBottomCount`：通过 `parentId` 递归归属到当前锅型根节点下的锅底数。
3. `rawBottomCandidateCount`：同一批接口数据里疑似锅底行的数量，用于辅助判断接口是否完整但父子关系异常。
4. `missingSlots`：按接口数组顺序落位后缺失的锅位标签。

#### 2.2.4 判定状态

| 状态 | 条件 | 含义 | 建议处理 |
| --- | --- | --- | --- |
| `Complete` | `attachedBottomCount == expectedSlotCount` | 结构完整 | 允许正常展示、匹配配方、执行加水 |
| `IncompleteFromApi` | `rawBottomCandidateCount < expectedSlotCount` | 接口返回的锅底本身不足 | UI 明确提示锅底缺失，不允许静默执行 |
| `ParseLostSuspected` | `rawBottomCandidateCount >= expectedSlotCount` 且 `attachedBottomCount < expectedSlotCount` | 接口可能完整，但 `parentId` 或锅底候选判断导致解析漏了 | UI 明确提示结构异常，记录日志，禁止自动下发 |
| `Overflow` | `attachedBottomCount > expectedSlotCount` | 当前锅型下归属了过多锅底 | UI 明确提示结构异常，禁止自动下发 |

#### 2.2.5 UI 展示规则

1. UI 应按锅型展示固定数量的物理卡片，例如四宫格永远展示 4 个卡片。
2. 如果某个锅位缺失，不允许用第一个锅底名、锅型 Code 或兜底配方伪装成有效锅底。
3. 缺失锅位应直接显示：`接口未返回锅底` 或 `订单结构异常`。
4. 锅底详情仍只展示操作员需要的信息：锅底名、口味/备注、底料信息、鲜辅料。
5. 结构校验的工程细节，例如 `expectedSlotCount`、`attachedBottomCount`、`rawBottomCandidateCount`、`missingSlots`，应放到设置/维护/调试页或日志中，不混入首页普通卡片。

#### 2.2.6 执行保护

1. 结构不完整或结构异常的订单，不应自动进入相位规划和 PLC 下发。
2. 如果后续现场需要“允许操作员强制继续”，必须单独设计人工确认流程，并在日志中记录强制执行原因。
3. 在没有强制确认机制前，默认策略是阻止加水，避免错误锅位、错误配方或错误辅料执行。

#### 2.2.7 实现建议

1. 在订单解析层新增 `OrderStructureValidator` 或等价纯函数，不放在 Compose UI 中。
2. `PosOrderTaskAssembler` 负责组装任务树后调用结构校验，并把校验结果写入订单模型或运行诊断模型。
3. `PotDetailPresenter` 只消费已解析好的展示模型，不自行判断锅底是否缺失。
4. `PhaseCommandPlanBuilder` 或相位规划入口在收到结构异常订单时直接拒绝生成 PLC 命令。
5. 增加单元测试覆盖：四宫格 4 个锅底正常、四宫格少 1 个锅底、接口完整但 `parentId` 异常、锅底候选字段形态异常、超出期望锅底数。

## 3. 实体主键与事件关联指纹

订单实体和 POS 操作事件使用不同身份：

1. 301：`localTaskId = root.id`，重复轮询同一根记录保持幂等。
2. 302/303/304：事件根 `id` 用于事件幂等，`Base_Hash` 用于查找候选实体。

### 3.1 基础特征指纹 (Base Hash)
公式：
`Base_Hash = MD5( ikmsOrder + Root_posFoodCode + ArrayOrder_Child_FoodCodes )`

*   `ikmsOrder`：账单流水号，绑定具体的客人就餐批次。
*   `Root_posFoodCode`：锅体类型（如四宫格的商品码）。
*   `ArrayOrder_Child_FoodCodes`：**【极度重要】**该锅体下所有汤底和口味的商品码，**必须严格保留其在原始 JSON 数组中出现的先后顺序进行拼接，绝不允许自行排序**。因为数组出现的先后顺序，直接决定了物理机器上的 1、2、3、4 号落位宫格。如果成分相同但位置不同（如红油在1号位 vs 红油在2号位），它们将被识别为两口完全不同的锅。

### 3.2 同款多锅

同桌同账单可以存在多口完全相同的锅，它们拥有相同 `Base_Hash`，但301根 `id` 不同，因此在 Room 中是不同实体。事件命中多个候选时按 `operateTime + id` FIFO，每个事件只消费一条。

## 4. 关键操作码 (Operation) 处理状态机

轮询获取的数据必须根据 `operation` 字段分发到不同的处理管道。

### 🔘 `operation: 301` (正常下单)
*   **动作**：提取整棵树，以301根 `id` 建立实体，同时计算事件关联 `Base_Hash`。
*   **数据库交互**：执行 `INSERT OR IGNORE`。
*   **状态**：若主键不存在，存入数据库并初始化为 `PENDING`，加入打锅机待制作队列；若已存在则静默忽略。

### 🔘 `operation: 303` (退单 / 作废)
> [!CAUTION]
> 303 操作自带全新的 `id`，必须依靠 `Base_Hash` 去数据库中实施“模糊追杀”。
*   **动作**：计算该退单树的 `Base_Hash`。在本地数据库查询 `LIKE '{Base_Hash}_%'`。
*   **数据库交互**：
    1.  若找到的任务状态为 `PENDING`：将其置为 `CANCELED`，成功拦截，不予制作。
    2.  若找到的任务状态为 `RUNNING` 或 `COMPLETED`：订单已下发下位机或已出锅，系统强制触发屏幕**【红色警报】**，提示人工处理物理退锅。

### 🔘 `operation: 304` (换桌 / 转台)
> [!NOTE]
> 伴随 `turnTableCode` (旧桌号) 和 `tableCode` (新桌号)。
*   **动作**：计算该转台树的 `Base_Hash`，在本地数据库查询 `LIKE '{Base_Hash}_%'`。
*   **数据库交互**：无需撤销任务。找到匹配项后，直接执行 `UPDATE` 操作，将旧 `tableCode` 修改为新 `tableCode`。界面 UI 会通过 Flow 自动热刷新桌号显示。

## 5. 后续核心系统对接 (预留)

*(本节为架构扩展预留，待业务逻辑最终确认后详细设计)*

### 5.1 机器注册与鉴权接口 (Device Registration)

为确保云端精准下发专属于本台物理设备的订单与配方，上位机软件在出厂或重置后，必须遵循严格的“两步走（Two-Step）”级联注册协议获取身份 ID。

1. **第一步：获取门店设备类型 (Fetch Device Type)**
   * **接口**：`GET /pot/getDeviceType`
   * **作用**：获取该门店下所有的设备分类。实施人员需在界面中选取当前机型对应的 `deviceTypeCode`（例如：“打锅机”对应的 `POT2504231044380003`）。
2. **第二步：获取实体机器标识 (Fetch Equipment)**
   * **接口**：`POST /pot/getEquipment`
   * **请求格式**：`x-www-form-urlencoded`
   * **入参**：`deviceTypeCode` (如上步获取)。
   * **作用**：获取该类型下真实的物理机器列表。用户在界面上选中具体机器（例如：“打锅机01”）。系统返回包含门店码、时间戳等极长规则拼接的 **`deviceCode`**（例如：`POT25042310443800031347332507281551070016`）。
3. **本地身份绑定**：
   上位机将最终选定的 `deviceCode` 永久化存储（如 `SharedPreferences`）。在随后的整个生命周期内，所有向上游的请求（订单轮询、配方拉取等）均以此 `deviceCode` 作为唯一身份锚点。

### 5.2 汤底配方获取接口 (Recipe Management API)

打锅机的核心“烹饪引擎”依赖于配方库。该模块负责将订单中的商品码翻译为真实的 PLC 泵机参数（如：加水量、加鸡油量等）。

1. **2D 联合寻址法则 (Two-Key Lookup)**：
   *   订单树中的**子节点 `posFoodCode`** 对应配方库的 `potCode`（如：`90008439` = 有料真香锅）。
   *   订单树中的**根节点 `posFoodCode`** 对应配方库的 `potTypeCode`（如：`01-0154-012003` = 四宫格）。
   *   通过这两个 Key 的交叉匹配，精准提取对应锅体大小下特定汤底的执行参数（如：`addWater: 1.50`）。

2. **配方全量轮询策略 (Full-Sync Polling)**：
   *   上位机启动一个后台任务，以固定的频率（例如：每 1 分钟）通过 `POST /pot/getFormula`（且仅传 `deviceCode`）向云端发起全量配方拉取。
   *   拉取到的几百种配方数据全量覆盖写入本地 Room 数据库的配方表。

3. **订单配方的热更新 (Dynamic Order Update)**：
   *   当配方轮询任务检测到云端配方发生变更并完成本地更新后，系统将自动扫描当前处于 `PENDING_WATER`（待加水）和 `PENDING_DELIVERY`（待传锅）状态的订单。
   *   如果订单关联的配方参数发生了改变，系统将利用最新的配方详情，动态更新这些排队中订单的加料参数，确保即将打出的锅底采用最新“秘籍”。

4. **后台 UI 映射与双向同步 (Two-Way Sync)**：
   *   在 Android 系统的 **“设置 (Settings) -> 配方管理”** 页面，店长可以微调“加水、鸡油、骨膏”等流体参数。
   *   **【极度巧妙的设计：时间驱动而非容量驱动】**：配方接口中下发的 `addWater: 2.0`、`addChickenOil`、`boneOil` 等数值，其物理单位**并非升(L)或克(g)**，而是**绝对时间：秒(S)**。这意味着上位机无需进行复杂的流速换算，直接将此数值下发给 PLC 即可控制对应水泵的开启时长。若门店发现水泵老化出水量变小，店长只需在屏幕上将时间改长（如 2.0s -> 2.5s），即可完美自适应硬件损耗。
   *   **防覆盖机制**：本地一旦修改并保存，立刻暂停 1 分钟全量轮询。调用 `POST /pot/updateEquipmentParam` 接口，传入 `deviceCode`, `potCode`, `potTypeCode` 及修改后的参数（时间值）。
   *   云端返回成功后，本地数据库持久化该修改，并恢复轮询任务。下次轮询将拉取到云端的最新值，实现真正的云端-本地双向互通。

## 6. 订单业务状态流转与特殊标记

根据打锅机的真实业务场景，订单在 Room 数据库中必须维护一套严谨的生命周期状态（State Machine）和业务标记。

### 6.1 核心生命周期状态 (Status)
1.  **待加水 (PENDING_WATER)**：
    *   触发条件：收到 POS `301` 下单报文且成功入库。
    *   含义：排队中，尚未下发给 PLC 开始动作。
2.  **待传锅 (PENDING_DELIVERY)**：
    *   触发条件：下位机（PLC）反馈“加水/加料动作已执行完毕”。
    *   含义：锅底已经打好，正停放在打锅机工位上，等待服务员端走。
3.  **已完成 (COMPLETED)**：
    *   触发条件：传感器检测到锅被端走，或服务员在屏幕手动点击确认。
    *   含义：生命周期结束，从待办列表中移除。
    *   **平台握手回调**：状态变更为已完成时，必须立刻触发 `POST /pot/order/feedback` 接口，向云端 POS 发送 `deviceId` 和 `orderId`，告知前厅“这口锅已经做好被端走了”，完成订单在 POS 系统的最终闭环。
4.  **已取消 (CANCELED)**：
    *   **自动取消 (CANCELED_AUTO)**：通过 POS 轮询系统收到 `303` 退菜报文，由系统自动拦截并置为取消。
    *   **手动取消 (CANCELED_MANUAL)**：员工由于特殊原因（如打错料、洒了等），直接在打锅机 Android 屏幕上手动点击作废。

### 6.2 业务附属标记 (Flags)
除了核心状态，由于前厅客人的动态需求，订单实体还需要包含额外的状态修饰符（布尔值或时间戳）：
*   **催单 (isUrged)**：
    *   触发条件：前厅点击催菜。
    *   行为：在打锅机屏幕上高亮飘红显示，或强行提升排队优先级插队制作。
*   **延时 (isDelayed)**：
    *   触发条件：客人未到齐要求“叫起”或“延时上锅”。
    *   行为：在屏幕上挂起该任务，锁定不可下发 PLC，倒计时结束后恢复为正常“待加水”状态。
