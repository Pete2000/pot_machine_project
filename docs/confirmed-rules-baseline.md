# 当前已确认规则基线

这份文档用于记录当前项目里已经可以作为“准标准”的规则。

原则：

1. 真实接口返回优先于旧 PDF 文档
2. 真实调用截图优先于旧 PDF 文档
3. 当前对话里已经明确的现场控制规则，可作为临时标准继续建模

---

## 1. 数据来源优先级

当前按下面优先级认定：

1. 真实接口返回
2. 真实调用截图
3. 现场实际控制说明
4. 旧版 PDF / Word 文档

如果几者冲突：

1. 先以真实接口返回为准
2. 再以现场实际控制说明修正
3. 旧文档只作为参考，不作为最终依据

---

## 2. 订单接口基线

### 2.1 当前已确认

1. 订单接口地址形态为
   `http://IP:8050/pos/order/query`
2. 订单是树状结构
3. `parentId` 是串联订单树的关键字段
4. 一条锅型记录是根节点
5. 一条锅底记录挂在锅型节点下面
6. 一条口味记录挂在锅底节点下面

### 2.2 当前默认解析规则

1. `potTypeCode != null && parentId == null`
   表示锅型节点
2. `potBottomCode != null && parentId = 锅型节点.id`
   表示锅底节点
3. `tasteCode != null && parentId = 锅底节点.id`
   表示口味节点

### 2.3 当前业务理解

每一个锅位最终都应解析成：

`锅型 + 锅底 + 口味 + 备注`

---

## 3. 配方接口基线

### 3.1 当前已确认

这部分以你提供的真实接口和真实返回为准。

1. 配方接口地址形态为
   `http://IP:8050/pot/getFormula`
2. 当前真实调用方式按
   `POST`
   `x-www-form-urlencoded`
   认定
3. 当前真实请求参数包含
   `deviceCode`
   `potCode`
   `potTypeCode`
   `formulaCode`
4. 当前真实返回里包含
   `formulaCode`
   `formulaName`
   `whetherDefault`
   `pots`
5. 每个锅底下再按锅型返回
   `potTypeCode`
   `potTypeName`
   `addWater`
   `addChickenOil`
   `boneOil`
   `materials`
   `basicMaterials`

### 3.2 当前强规则

1. 配方匹配不能只看 `potCode`
2. 必须至少按 `potCode + potTypeCode` 匹配
3. 同一个锅底在
   `单锅 / 拼锅 / 四宫格`
   下的配方可能不同
4. `addWater`、`addChickenOil`、`boneOil` 当前按秒值理解
5. `boneOil` 以真实返回字段名为准，不用旧 PDF 的 `bone_oil`

### 3.3 当前待继续收敛但先这样使用

1. 当接口返回多个 `formulaCode` 时，当前先以真实返回整体作为有效结果集
2. `whetherDefault` 已确认存在，但最终选择规则暂未完全固化
3. 在没有更强业务规则前，可先优先关注真实请求所返回的当前有效配方集合

## 4. 控制规则基线

### 4.1 出水口与锅位

当前按下面固定理解：

1. `1 = 左上`
2. `2 = 右上`
3. `3 = 左下`
4. `4 = 右下`

### 4.2 锅型执行规则

1. 单锅
   4 个出水口同时出同一种锅底
2. 拼锅
   左侧 `1 + 3` 出一种锅底
   右侧 `2 + 4` 出一种锅底
3. 四宫格
   `1 / 2 / 3 / 4` 各出各自锅底

### 4.3 辅料规则

1. 鸡油和骨膏出料口在左上角工位
2. 是否需要鸡油、骨膏，不再靠口味文字判断
3. 一律由锅底配方接口里的
   `addChickenOil`
   `boneOil`
   决定
4. 当 `addChickenOil > 0` 或 `boneOil > 0` 时，该锅底必须走左上角辅料工位

### 4.4 人工转锅规则

1. 转锅不是自动执行
2. 转锅由人工完成
3. 系统负责弹窗提示
4. 操作员转锅后点击确认
5. 系统继续该锅位剩余的水和料
6. 人工转锅确认当前按安卓弹窗为准，不结合物理按键
7. 如果多个锅位都要辅料，先处理当前左上角可执行锅位，再提示人工转锅继续
8. 当多个锅位都可作为下一次左上优先锅位时，当前固定优先级为
   `左上 -> 左下 -> 右上 -> 右下`

## 5. 当前代码模型对应关系

当前代码里的关键对象可按下面理解：

1. `PosOrderLine`
   对应订单接口单条记录
2. `PotOrderParser`
   负责把 `parentId` 树还原成锅位任务
3. `PotRecipeProfile`
   对应锅底配方
4. `ParsedPotOrder`
   表示订单解析后的锅位任务
5. `DispatchPlan`
   表示最终控制计划

## 6. 当前最可靠的项目共识

如果现在继续学习或继续建模，优先按这几条走：

1. 订单负责表达结构
2. 配方负责表达控制参数
3. `parentId` 决定树结构
4. `potCode + potTypeCode` 决定配方
5. `addChickenOil/boneOil > 0` 决定是否必须去左上角
6. 左上角之外需要辅料时，走人工转锅确认流程

## 7. 最新补充共识

1. 加水阶段的启动应理解为“统一启动”。
2. 加水阶段的停止应理解为“按各锅位配方独立停止”。
3. 如果左上角锅位正在执行鸡油或骨膏，而另一个非左上锅位也需要鸡油或骨膏，则该非左上锅位不能与左上角同时执行辅料。
4. 这类非左上锅位连加水也必须等人工转锅后再执行。
5. 只要整单里存在需要鸡油或骨膏、但当前不在左上角的锅位，就应优先先把其中一个转到左上角，再开始这轮执行。
6. 当前选中的左上工位，如果鸡油和骨膏都需要，则两者允许同时执行。
7. 对于需要延后的非左上辅料锅位，其加水应在转锅后的同一相位里，与鸡油和骨膏一起执行。
8. 加热命令需要纳入同一套 `commandId` 协议。
9. 安全保护的最终放行权归 PLC，PLC 拥有绝对保护权。
10. 这条限制是为了避免飞溅，优先级高于“同相位可并发”的简化建模。
