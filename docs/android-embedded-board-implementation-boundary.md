# 打锅机 Android 屏 + 嵌入式控制板功能与控制边界说明

本文档用于对接 Android 工业屏、嵌入式控制板和整机控制方案团队。

当前项目已经按 Android 上位机 + PLC 下位机跑出了一套可复用的业务经验。后续如果硬件方案调整为 Android 屏 + 嵌入式控制板，核心思路不是重新定义整套业务，而是保留现有上位机业务模型和控制边界，将原 PLC 执行层替换为嵌入式控制板执行层。

也就是说：

1. 订单、配方、锅位、相位、转锅提示、日志和版本管理仍由 Android 屏承载。
2. 阀、泵、加热、液位、急停、限位、输出互锁和安全保护由嵌入式控制板承载。
3. 原来 Android 与 PLC 之间的命令号、状态回传、故障码、心跳、幂等执行等经验，需要迁移为 Android 与嵌入式控制板之间的接口约定。
4. 嵌入式控制板可以自行决定 MCU 型号、RTOS 或裸机、协议帧格式、PCB 和驱动电路，但不能改变整机已经明确的业务和安全边界。

## 1. 整体架构

目标整机结构如下：

```text
门店 POS / 业务服务器
        |
        | 订单、锅型、锅底、口味、备注
        v
Android 工业屏
订单解析、配方匹配、相位规划、操作界面、本地记录、日志上传、APP 升级
        |
        | 控制命令、状态回传、故障码、心跳
        v
嵌入式控制板
阀、泵、加热、液位、急停、限位、转锅确认、安全联锁、执行状态机
        |
        v
水路、料路、加热器、转锅机构、液位传感器、温度传感器、急停和其他现场硬件
```

Android 屏不直接驱动物理输出。它负责把订单和配方转换成明确的相位命令，再下发给控制板。

嵌入式控制板不负责理解 POS 订单，也不负责决定锅底配方。它接收 Android 已经规划好的控制命令，校验参数，执行硬件动作，并返回真实设备状态。

## 2. 从当前 PLC 方案迁移到嵌入式板的原则

当前项目里的 PLC 可以理解为“现场执行器 + 安全兜底”。后续换成嵌入式控制板时，这个角色不变。

迁移时应保留以下经验：

1. Android 仍然是上位机，负责订单和业务流程。
2. 嵌入式板替代 PLC，负责底层执行和保护。
3. 设备实际状态以下位机返回为准，Android 不凭界面状态自行推断硬件安全。
4. 所有物理动作必须有命令号或等价的防重机制。
5. 相位执行、加热控制、应急补水或单独动作应分区处理，避免一个字段在不同命令里含义混乱。
6. 安全保护在下位机闭环，不依赖 Android 正常运行。
7. Android 重启、通信断开、订单重试时，不应导致阀、泵、加热或转锅动作重复执行。

迁移后，原 PLC 地址表可以不照搬，但它背后的控制分层需要保留：

1. 物理输入输出层：真实阀、泵、加热、传感器、急停。
2. 通信镜像层：Android 可读取的输入、输出、状态、故障。
3. 控制状态机层：嵌入式板内部的执行状态、计时、锁存、互锁。
4. 命令协议层：Android 下发的相位、加热、停止、复位等命令。

## 3. Android 屏负责的内容

Android 屏负责业务、人机界面、联网和记录。

明确由 Android 屏负责：

1. 从门店 POS 或业务服务器拉取订单。
2. 解析订单树结构，识别锅型、锅底、口味和备注。
3. 拉取锅底配方。
4. 按锅型 Code + 锅底 Code 匹配配方，名称只作为兜底。
5. 按接口数组顺序确定锅底顺序，不使用 `potSort` 改执行顺序。
6. 将订单转换成单锅、拼锅、四宫格的锅位任务。
7. 根据加水、鸡油、骨膏时长生成相位计划。
8. 判断哪些锅位必须进入左上角辅料工位。
9. 触发人工转锅提示，并在操作员确认后继续下一相位。
10. 生成下发给控制板的相位命令、加热命令、停止命令和复位命令。
11. 显示操作员需要的信息，包括当前订单、锅底详情、执行状态、转锅提示、故障提示和恢复入口。
12. 保存本地订单、执行状态、操作记录和故障日志。
13. 对接管理服务器，完成 APP 升级、日志上传、设备配置和设备状态上报。

Android 屏不负责：

1. 直接驱动阀、泵、加热、电机等物理输出。
2. 绕过控制板的急停、缺水、过温、通信超时等安全保护。
3. 在没有下位机真实状态回传时继续假定设备安全。
4. 在重启后凭本地旧状态继续执行物理动作。

## 4. 嵌入式控制板负责的内容

嵌入式控制板负责硬件执行、实时状态和安全保护。

明确由嵌入式控制板负责：

1. 接收 Android 下发的控制命令。
2. 校验命令号、命令类型、参数范围和当前是否允许执行。
3. 锁存有效命令，防止同一命令重复触发物理动作。
4. 控制多路出水阀。
5. 控制鸡油泵。
6. 控制骨膏泵。
7. 控制主加热器和备用加热器。
8. 控制总进水、单独补水或应急补水相关输出。
9. 读取急停、液位、温度、限位、按钮和其他传感器。
10. 执行液位补水、急停保护、过温保护、主备加热互斥、备用泵互斥等底层规则。
11. 维护执行状态机，包括空闲、已接收、执行中、完成、停止、故障。
12. 周期性向 Android 回传真实输入、真实输出、命令执行状态和故障码。
13. 检测 Android 心跳或通信超时，并在超时时进入安全状态。
14. 上电默认关闭危险输出，等待 Android 重新握手。

嵌入式控制板不负责：

1. 解析 POS 订单。
2. 拉取锅底配方。
3. 判断锅底名称、口味或备注。
4. 决定单锅、拼锅、四宫格的业务拆分。
5. 改写客人的逻辑锅位顺序。
6. 决定哪个锅底先执行、哪个锅位先转到左上角。
7. 上传 APP 日志或替代 Android 完成业务侧管理功能。

一句话：

`Android 负责把业务计划算对，嵌入式板负责把当前命令安全执行完。`

## 5. 订单与配方规则

这部分是当前项目已经明确的业务规则，嵌入式板方案不能重新解释。

### 5.1 订单结构

订单按树状结构解析：

1. 锅型记录是根节点。
2. 锅底记录挂在锅型节点下面。
3. 口味记录挂在锅底节点下面。
4. 每个锅位最终形成“锅型 + 锅底 + 口味 + 备注”的任务。

### 5.2 配方匹配

配方匹配规则：

1. 不能只看锅底名称。
2. 不能只看锅底 Code。
3. 必须优先使用锅型 Code + 锅底 Code 匹配。
4. 同一个锅底在单锅、拼锅、四宫格下可能对应不同配方。
5. `addWater`、`addChickenOil`、`boneOil` 按配方返回值生成控制参数。

### 5.3 锅底顺序

锅底顺序以接口数组顺序为准。

不使用 `potSort` 作为执行顺序依据。这个规则已经在当前项目里作为硬约束处理，后续嵌入式板方案不能改成按 `potSort` 排序。

## 6. 锅位与相位规则

当前按四个逻辑锅位理解：

1. 1 号位：左上
2. 2 号位：右上
3. 3 号位：左下
4. 4 号位：右下

支持三类锅型：

1. 单锅：四个锅位执行同一种锅底。
2. 拼锅：左侧 1 + 3 为一种锅底，右侧 2 + 4 为另一种锅底。
3. 四宫格：1、2、3、4 各自执行自己的锅底。

加水阶段采用“统一启动、独立停止”的模型：

1. 一个相位可以同时启动多个出水位。
2. 各出水位按自己的配方时长独立停止。
3. 相位内的出水时长由 Android 计算并下发。
4. 控制板负责计时、输出和停止。

控制板只执行当前相位，不改写逻辑锅位。

例如 Android 下发当前相位：

```text
phaseCommandId = 1024
phaseNo = 1
slotMask = 0b1111
water1 = 80
water2 = 65
water3 = 80
water4 = 65
activeTopLeftSlot = 1
chickenOil = 20
bonePaste = 0
```

控制板需要理解的是：这条相位命令当前是否有效、哪些输出要执行、执行多久、完成后回传什么状态。它不需要重新推导为什么 1 号位是左上、为什么某个锅底要加鸡油。

## 7. 鸡油、骨膏和左上角规则

当前机械和业务规则固定为：

1. 鸡油出料口在左上角工位。
2. 骨膏出料口在左上角工位。
3. 是否需要鸡油或骨膏，由配方字段决定，不靠口味文字猜。
4. `addChickenOil > 0` 表示需要鸡油。
5. `boneOil > 0` 表示需要骨膏。

执行规则：

1. 当前已经在左上角的锅位，如果需要鸡油或骨膏，可以在当前相位执行。
2. 当前不在左上角的锅位，如果需要鸡油或骨膏，必须先提示人工转锅。
3. 对于需要延后的非左上辅料锅位，加水也应在转锅后的同一相位内与鸡油、骨膏一起执行。
4. 如果左上角锅位正在执行鸡油或骨膏，其他非左上且也需要辅料的锅位不能同时执行辅料。
5. 当前选中的左上工位如果鸡油和骨膏都需要，鸡油和骨膏允许同相位执行。

这条规则的目的不是单纯业务排序，而是避免料口位置不一致、辅料喷错锅位和现场飞溅风险。

## 8. 转锅规则

当前项目按人工转锅理解：

1. 转锅不是由系统自动完成。
2. Android 负责提示操作员需要转锅。
3. 操作员完成转锅后，在 Android 屏确认。
4. Android 再下发下一条相位命令。
5. 控制板不主动决定下一锅应该转到哪里。

如果后续硬件升级为自动转锅，可以在控制板侧增加定位和执行能力，但业务边界仍然不变：

1. Android 决定哪个逻辑锅位要成为当前左上工位。
2. 控制板执行转锅动作并回传是否到位。
3. 到位确认后才允许执行鸡油、骨膏和对应加水动作。

如果没有自动转锅硬件，则控制板至少需要能回传等待转锅、允许执行、禁止执行等状态，避免 Android 在未确认情况下继续下发危险动作。

## 9. 建议保留的命令模型

不要求嵌入式板照搬 PLC 寄存器地址，但建议保留当前项目已经验证过的命令分区思想。

### 9.1 相位命令

相位命令用于执行一次打锅动作。

建议包含：

1. `phaseCommandId`：相位命令号。
2. `phaseCommandType`：执行、停止、复位等类型。
3. `slotMask`：本相位参与的逻辑锅位集合。
4. `waterDuration1`：当前物理左上出水位时长。
5. `waterDuration2`：当前物理右上出水位时长。
6. `waterDuration3`：当前物理左下出水位时长。
7. `waterDuration4`：当前物理右下出水位时长。
8. `activeTopLeftLogicalSlot`：当前左上工位服务的是哪个逻辑锅位。
9. `chickenOilDuration`：鸡油时长。
10. `bonePasteDuration`：骨膏时长。
11. `phaseNo`：相位号。
12. `checksum` 或等价校验。

单位可以由承接团队定义，但必须固定，例如 100ms、10ms 或 ms，不能同一字段在不同场景下单位变化。

### 9.2 相位状态

相位状态至少应回传：

1. 已接收命令号。
2. 正在执行命令号。
3. 已完成命令号。
4. 当前相位状态：Idle、Accepted、Running、Completed、Stopped、Fault。
5. 执行结果码。
6. 故障码。
7. 剩余时间或剩余 tick。
8. 当前实际输出状态。

Android 必须通过这些状态判断当前命令是否真正被接收、是否正在执行、是否完成或失败。

### 9.3 加热命令

加热命令应与相位命令分开，不要和相位字段复用。

建议包含：

1. `heaterCommandId`。
2. `heaterCommandType`。
3. 主加热或备加热选择。
4. 目标温度。
5. 回差或控制参数。
6. 温度传感器选择。
7. 命令版本或校验。

控制板负责最终判断是否允许加热。急停、液位异常、温度异常、主备互斥不满足时，应拒绝或关闭加热输出。

### 9.4 应急补水和手动动作

应急补水、单独加水、单独鸡油、单独骨膏、备用泵切换等动作应与正式订单相位分开处理。

这些动作必须满足：

1. 有独立命令类型。
2. 有独立状态回传。
3. 有防重机制。
4. 受急停、液位、互锁等安全规则限制。
5. 不污染正在执行的订单相位状态。

## 10. 幂等、防重与恢复

这是当前项目经验里非常关键的一点。

Android 可能因为按钮连点、网络重试、进程重启、通信超时而重复发送同一条命令。控制板不能把每次收到的数据都当成新动作。

要求：

1. 同一个 `commandId` 只允许被同一执行域接收一次。
2. 如果重复收到已接收或执行中的命令，应返回当前状态，而不是重新启动输出。
3. 如果重复收到已完成命令，应返回已完成结果，而不是再次执行。
4. 新命令到来时，控制板要判断当前是否空闲或是否允许打断。
5. 停止命令和复位命令要有明确状态变化，不能和执行命令混在一起。
6. Android 重启后，必须先读取控制板真实状态，再决定是继续显示、停止、复位还是重新同步订单。

这部分如果不做清楚，现场最容易出现“订单重复执行”“阀又开了一次”“加热状态显示和真实输出不一致”的问题。

## 11. 安全保护

控制板必须拥有最终安全放行权。

以下规则必须在控制板侧成立：

1. 急停触发时，危险输出立即关闭。
2. 通信超时时，阀、泵、加热、转锅等输出进入安全状态。
3. 液位超低时，禁止可能导致干烧或异常出料的动作。
4. 温度异常或过温时，禁止加热或关闭加热。
5. 主加热和备加热不能违背互斥规则。
6. 备用泵不能同时承担鸡油和骨膏。
7. 上电默认关闭危险输出。
8. 参数非法时拒绝执行，不以默认值悄悄执行。
9. 控制板故障时要回传明确故障码。

Android 可以提示、记录和上报这些故障，但不能绕过它们。

## 12. 状态与故障码

控制板需要给 Android 提供稳定、可长期维护的状态和故障定义。

状态至少包括：

1. 空闲。
2. 命令已接收。
3. 执行中。
4. 执行完成。
5. 已停止。
6. 故障。
7. 等待转锅确认。
8. 通信超时保护。

故障至少应覆盖：

1. 急停。
2. 液位不足。
3. 温度异常。
4. 加热保护。
5. 输出互锁失败。
6. 命令参数非法。
7. 命令执行超时。
8. 传感器异常。
9. 通信异常。
10. 控制板内部错误。

故障码需要稳定，不要频繁变动。Android 会基于故障码做现场提示、日志上传和售后排查。

## 13. 本地记录、日志和管理服务器

Android 侧需要继续保留当前项目已有的本地可靠存储思路。

要求：

1. 订单和执行状态本地保存。
2. 命令下发、状态回传、故障和关键操作需要记录。
3. APP 重启后能恢复当前订单视图和设备状态。
4. 管理服务器用于 APP 版本升级、日志上传、设备配置和故障追踪。
5. 控制板如果有独立固件版本，也应能被 Android 读取并上传。

门店 POS 通信可以按现场实际保留内网 HTTP，但管理服务器、升级包和日志通道应单独考虑安全边界。

## 14. 对承接团队的交付要求

承接团队输出方案时，不是重新讨论需求，而是围绕上述边界给出落地设计。

至少需要交付：

1. Android 屏与嵌入式控制板的系统架构图。
2. 控制板 IO 清单。
3. 每一路阀、泵、加热、转锅、传感器的定义。
4. Android 与控制板通信协议。
5. 相位命令定义。
6. 加热命令定义。
7. 应急/手动动作命令定义。
8. 状态码和故障码定义。
9. 命令防重和恢复策略。
10. 心跳和通信超时策略。
11. 安全联锁策略。
12. 固件版本读取和升级策略。
13. 台架测试方案。
14. 现场验收方案。

这些交付物必须能覆盖当前项目已经形成的业务规则，而不是只证明单个 IO 能开关。

## 15. 最小联调验收项

第一轮样机联调至少要验证：

1. Android 能连接控制板并读取固件版本。
2. Android 能读取输入状态和输出状态。
3. Android 能下发相位命令。
4. 控制板能返回 Accepted、Running、Completed。
5. 同一相位命令重复发送不会重复执行。
6. 单锅、拼锅、四宫格均能生成正确相位。
7. 加水能统一启动并独立停止。
8. 左上角锅位能执行鸡油和骨膏。
9. 非左上角需要辅料时，必须先进入转锅确认流程。
10. 停止命令能关闭当前相位输出。
11. 复位命令能清理相位状态，但不能绕过安全保护。
12. 急停触发后危险输出关闭。
13. 液位异常时相关动作被禁止。
14. 温度异常时加热被禁止或关闭。
15. Android 断开通信后控制板进入安全状态。
16. Android 重启后能读取控制板真实状态并恢复界面。
17. 故障码能被 Android 显示、记录并上传。
18. APP 升级和日志上传链路可用。

## 16. 结论

后续方案不应被理解为“重新做一套打锅机控制系统”，而应理解为：

`保留当前 Android 上位机项目已经验证过的订单、配方、相位、转锅和日志经验，把 PLC 下位执行层替换为嵌入式控制板。`

Android 屏负责业务正确性和现场操作体验。

嵌入式控制板负责硬件执行真实性和安全保护。

双方通过明确的命令、状态、故障、心跳和防重机制连接起来。只要这个边界清楚，后续具体使用 STM32、GD32、RTOS、裸机、RS485、CAN 或自定义协议，都属于承接团队的实现选择，不应改变整机功能和安全原则。
