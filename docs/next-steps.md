# 当前阶段修补与硬件阶段待办

更新日期：`2026-05-30`

这份文档用于记录：

1. 当前已经完成的低风险修补
2. 明确哪些问题故意留到硬件联调阶段再处理
3. 避免后续把“可先改的稳定性问题”和“必须结合硬件验证的大改”混在一起

---

## 1. 当前结论

当前项目已经完成一轮**不影响后续硬件测试**的低风险修补。

这一轮没有做以下高风险动作：

1. 没有把订单主链路切到正式 `/pos/order/query`
2. 没有把 PLC 下发主链路切到正式 `D300 ~ D379`
3. 没有把 `MockModbusTransport` 替换为真实串口 / RS485 实现
4. 没有重构自动运行、手动加水、相位推进主流程

因此，这一轮的目标不是“完成正式联调版”，而是先把当前代码变成一个更稳的软联调底座。

## 2. 本轮已完成修补

## 2.1 订单失败回写

已修补问题：

1. 订单在 `markStarted()` 成功后，如果 `plcController.dispatch()` 抛异常，后端可能收不到失败结束状态

当前处理：

1. 如果开始状态已经上报成功，但后续下发失败，会补发失败 `markFinished()`
2. 这样可以避免后端订单卡在“已开始但永不结束”的状态

相关文件：

1. `app/src/main/java/com/example/plccontroller/runtime/MachineCoordinator.kt`

## 2.2 Modbus 读帧长度校验

已修补问题：

1. 读线圈、读寄存器时只做了最低长度校验
2. 如果现场出现短帧、截断帧、脏帧，代码可能越界或误解析

当前处理：

1. 增加返回帧总长度校验
2. 增加 `byte count` 校验
3. 读帧格式不对时直接按通讯错误处理

相关文件：

1. `app/src/main/java/com/example/plccontroller/data/plc/ModbusRtu.kt`

## 2.3 HTTP 请求收尾与响应容错

已修补问题：

1. `HttpURLConnection` 没有显式 `disconnect()`
2. 待处理订单接口默认只接受“裸数组”响应

当前处理：

1. 请求结束后统一 `disconnect()`
2. 待处理订单接口同时兼容：
   - `[...]`
   - `{"data":[...]}`
   - `{"items":[...]}`
   - `{"rows":[...]}`

说明：

1. 这里只做了温和兼容
2. 没有改正式订单主链路

相关文件：

1. `app/src/main/java/com/example/plccontroller/data/http/OrderApiClient.kt`

## 2.4 设置页展示真实生效配置

已修补问题：

1. 配置虽然已经通过 `SettingsStore` 动态生效
2. 但设置页很多字段仍显示 `AppConfig` 编译期默认值

当前处理：

1. 设置页改为展示当前持久化并实际生效的配置
2. 包括：
   - 业务地址
   - 管理地址
   - 设备编码
   - PLC 从站号
   - 当前订单轮询间隔

意义：

1. 以后现场改参数时，UI 展示和实际运行值不会继续错位

相关文件：

1. `app/src/main/java/com/example/plccontroller/ui/MainViewModel.kt`
2. `app/src/main/java/com/example/plccontroller/ui/MainScreen.kt`
3. `app/src/main/java/com/example/plccontroller/ui/SettingsScreen.kt`
4. `app/src/main/java/com/example/plccontroller/ui/UiModels.kt`

## 2.5 减少高频无效状态重算

已修补问题：

1. `MachineRuntimeStore.update()` 之前每次更新都会重建 `transferDeck`
2. 即使只是日志、网络状态、提示文案变化也会重算

当前处理：

1. 只有在传锅卡组相关字段变化时才刷新 `transferDeck`
2. 降低高频轮询下的无效状态抖动

相关文件：

1. `app/src/main/java/com/example/plccontroller/runtime/MachineRuntimeStore.kt`

## 4. 明确留到硬件阶段再处理的项

下面这些不是忘了改，而是**有意延后**：

## 4.1 正式 PLC 协议切换

待处理内容：

1. 把当前原型寄存器下发切换到正式 `D300 ~ D379`
2. 让订单执行真正走相位命令、状态回读、转锅推进

当前不改原因：

1. 这部分强依赖真实 PLC 协议行为
2. 没有硬件时贸然切换，容易把“旧原型能跑”变成“新主链路也没法验证”

## 4.2 正式订单接入链路切换

待处理内容：

1. 切到 `/pos/order/query`
2. 接入 `PotOrderParser`
3. 接入 `PotDispatchPlanner`
4. 让订单真正走“锅型根节点 -> 锅底 -> 口味 -> 配方 -> 相位规划”

当前不改原因：

1. 后端真实返回、字段稳定性、去重规则、撤单改单行为都还需要联调确认

## 4.3 真实串口通信层

待处理内容：

1. 增加真实 `SerialPortManager`
2. 增加真实 RS485 / Modbus RTU 物理通信实现
3. 替换或抽离 `MockModbusTransport`

当前不改原因：

1. 没有硬件环境时只能写出“看起来对”的实现
2. 串口名、波特率、驱动、权限、超时特征都需要现场确认

## 4.4 手动加水 / 自动运行主流程

待处理内容：

1. `requestWater()` 不再只是提示语
2. `setAutomationEnabled()` 不再只是 UI 状态切换
3. 增加真正的相位推进与现场交互逻辑

当前不改原因：

1. 这部分会直接影响现场操作语义
2. 没有硬件和现场流程确认时，大改风险高

## 4.5 更大规模的模块重构

待处理内容：

1. 更细的模块拆分
2. 更完整的调度器划分
3. 更正式的串口层、协议层、订单层分层

当前不改原因：

1. 当前主要风险不在“拆得不够漂亮”
2. 而在“正式主链路尚未经过硬件真值验证”

## 5. 下一阶段推荐顺序

建议按下面顺序推进：

1. 保持当前这版代码作为软联调基础版
2. 等拿到最小可用硬件环境
3. 先验证真实通讯参数：
   - 串口
   - 从站号
   - 超时
   - 心跳
   - 基础读区是否正常
4. 再验证正式轮询区：
   - `M300 ~ M339`
   - `D200 ~ D214`
   - `D320 ~ D379`
5. 再决定是否切正式下发主链路
6. 正式下发跑通后，再切正式订单解析主链路
7. 最后再评估是否值得做更大规模重构

一句话：

`先确认真实通讯，再切正式协议，再切正式订单链路，最后再谈大改。`

---

## 6. 当前阶段不建议做的事

现阶段不建议：

1. 在没有硬件的情况下直接重写整个 PLC 下发流程
2. 在没有真实后端联调前全面替换订单主链路
3. 一边改正式协议，一边改串口层，一边改 UI 交互
4. 把“稳定性修补”和“体系重构”混在同一轮里做

原因：

1. 容易同时引入多组新变量
2. 后面一旦硬件不通，很难判断到底是协议错、串口错、状态机错，还是 UI 触发时机错
