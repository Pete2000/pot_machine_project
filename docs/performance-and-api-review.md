# 低配安卓主机与订单接口评审

## 1. 低配置安卓主机的实现原则

这个项目属于工业控制终端，不应该按普通消费类 App 的思路去做。

如果安卓主机配置不高，建议遵守下面这些原则：

1. UI 以稳定和响应快为第一目标，不追求复杂动画
2. 主界面只保留一个核心控制页，避免多层页面切换
3. 网络请求、串口通信、订单解析全部放后台线程
4. 所有列表都做增量刷新，不做整页重绘
5. 首页实时数据刷新频率控制在 300ms 到 1000ms 区间，不要高频刷新整个页面
6. 图片、阴影、渐变、模糊、透明叠层尽量减少
7. 不在主线程做 JSON 解析、日志拼接、串口收发和数据库写入
8. 故障弹窗、提示音、按钮状态切换必须简单直接，避免复杂过渡

## 2. 技术选型建议

当前工程骨架先用的是 Compose，适合快速搭原型。

但如果最终设备是以下情况，建议正式版改成传统 Android View：

1. Android 8/9 时代的工业平板
2. 2G 内存或更低
3. CPU 性能一般，且同时还要跑串口、日志、心跳、保活
4. 屏幕分辨率不高，但要求长时间持续亮屏运行

原因不是 Compose 不能用，而是传统 View 在这类设备上更稳、更好控、更容易做极限优化。

推荐组合：

1. 单 Activity
2. XML 布局
3. RecyclerView 展示订单队列
4. ViewModel + Coroutine 做状态管理
5. Room 或轻量 SQLite 做离线缓存

## 3. 从现场界面图看，页面应该拆成什么

从现场图片看，界面更接近“工业主控台”，不是普通点单页。

建议页面固定拆成 5 个区块：

1. 顶部状态栏
   包含时间、运行模式、联网状态、PLC 通讯状态
2. 设备状态区
   包含水箱温度、水位、加热状态、用电量、用水量
3. 操作按钮区
   包含催单、暂停/继续、手动加工、清空告警、转台或改单处理
4. 订单队列区
   列表字段建议固定为桌号、接收时间、锅型、锅底、营业员、状态
5. 当前锅底详情区
   展示当前选中订单的锅底名称、配方说明、克重、辅料、执行步骤

## 4. 界面交互建议

1. 所有主操作按钮必须大，且固定位置，不要滚动
2. 列表一次只展示最关键字段，详情放到下方固定详情区
3. 颜色只承担状态表达，不承担复杂装饰
4. “待单 / 加工中 / 完成 / 故障 / 转台”必须有统一颜色语义
5. 当前执行订单要高亮，且不能和普通待单视觉权重相同
6. 手动按钮和自动流程要明确分区，避免误触
7. 网络断开、PLC 断开、物料异常、出水超时都要在首页直接提示
8. 页面要支持常亮和误触容错，重要按钮最好有二次确认

## 5. 性能实现建议

1. 首页状态区采用定时局部刷新，不要整个页面反复 `setState`
2. 订单队列只在数据有变化时刷新
3. 订单详情区只在选中项变化时刷新
4. 串口轮询和 HTTP 轮询分离，分别限频
5. 日志区只保留最近 N 条，例如 50 条，防止内存上涨
6. 页面不要使用大图背景
7. 尽量不用实时图表、复杂阴影、模糊和透明遮罩
8. 所有异常提示要可恢复，不能因为一个接口超时把整个首页卡住

## 6. 当前订单接口文档存在的问题

现在这份 `锅底订单接口文档.docx`，本质上只有一个接口地址和一大段返回样例，还不能算完整接口规范。

目前主要问题如下：

1. 没写请求方式
   文档里只有 URL，没有明确说明是 `GET` 还是 `POST`
2. 没写请求参数
   没说明设备编号、门店编号、时间游标、分页参数、签名参数怎么传
3. 没写鉴权方式
   没说明是 token、header、签名还是白名单
4. 没写数据拉取规则
   没说明是全量拉取、增量拉取、按时间拉取，还是按设备拉取
5. 没写重复订单处理规则
   同一订单多次返回时，终端应去重还是覆盖，没有定义
6. 没写状态确认机制
   安卓端接到订单后，是否要回执“已接收 / 已开始 / 已完成 / 已失败”，文档里没有
7. 没写删除或撤单规则
   `operation = 301` 看起来像操作类型，但没有操作码定义
8. 没写字段说明
   大部分字段只有名字，没有语义、取值范围和是否必填说明
9. 没写层级关系规则
   目前只能从样例猜测 `parentId` 表示锅型、锅底、口味的树状关系，但文档没正式说明
10. 没写异常码规范
   只有 `success / msg / code`，但没有错误码清单
11. 没写时间字段时区和格式约束
   `operateTime/createTime/updateTime/testTime` 虽然看起来是字符串时间，但没有说明是否固定为北京时间
12. 没写空值约定
   很多字段有时是 `null`，有时是 `""`，终端需要明确区分还是统一按空处理，没有定义

## 7. 从样例数据里还能看到的风险

1. JSON 里出现了 `打汤机设备编号` 这种中文字段名
   这不利于多语言和客户端模型定义，建议统一改成英文键名
2. `potTypeCode`、`potBottomCode`、`tasteCode` 三者关系不清
   终端目前只能靠 `null` 和 `parentId` 猜测节点类型
3. `standardName` 既可能表示锅型，也可能表示锅底，也可能表示口味
   字段复用过度，终端不好直接做页面映射
4. `description` 既可能为空，也可能带备注
   需要明确它是配方说明、备注，还是操作指令
5. `potSort` 只在部分数据里有值
   如果它表示四宫格锅位序号，就必须对所有分锅场景有稳定定义
6. 没看到订单完成态字段
   目前更像“订单明细流”，不是“可直接执行的设备任务流”

## 8. 建议后端补充的正式接口规范

建议至少补齐下面这些内容：

1. 请求方式、路径、示例
2. 请求参数定义
3. 鉴权方式
4. 响应码与错误码表
5. 每个字段的含义、类型、是否必填、空值约定
6. `operation` 的枚举值定义
7. `parentId` 的层级关系图
8. 设备如何确认接单、开工、完工、失败
9. 是否支持撤单、改单、转台、补打
10. 增量拉取规则
11. 幂等规则
12. 重试规则和超时规则

## 9. 面向打锅机终端，建议后端直接给“设备任务视图”

如果后端愿意配合，最好不要让安卓终端自己从树状商品明细里拼装锅底任务。

更好的方式是后端直接返回设备任务，例如：

1. 一条任务对应一口锅位
2. 明确给出锅型、锅位号、锅底编码、口味编码、份数、备注
3. 明确给出任务状态
4. 明确给出是否可执行、是否已撤销、是否已转台

这样安卓端和 PLC 端都会简单很多，也更适合低配置设备稳定运行。

## 10. 当前已确认的订单树理解

根据最新沟通，接口样例里最关键的是 `parentId`。

当前可按下面方式理解：

1. 锅型节点是根
2. 锅底节点挂在锅型下面
3. 口味节点挂在锅底下面
4. 每一个锅位最终都应解析成
   `锅型 + 锅底名称 + 口味 + 备注`

这意味着终端不能只看单条记录，必须先还原成一棵订单树，再决定单锅、拼锅、四宫格以及锅位内容。
